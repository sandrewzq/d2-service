# T47：商人刷新差异与事件

> 状态：📝 候选方案，待细化与排期
> 优先级：P1
> 类型：事件驱动同步与库存差异

## 1. 目标

商人更新频率低，不增加固定轮询；只在明确事件发生时刷新，并让玩家知道本次刷新具体改变了什么。

这里的“配置变化”是指 Bungie 在不同刷新周期返回的 Offer 配置变化，不表示玩家购买时由应用生成随机 Roll。

## 2. 明确刷新事件

- 进入商人菜单。
- 切换商人。
- 账号页当前角色变化。
- 用户手动刷新。
- Xur 到访或离开边界。
- 应用恢复前台且确认已跨过当前商人的 `nextRefreshAt`。
- 权威账号快照更新且可能影响材料、声望或购买条件。
- 资料库激活新版本且商人或物品定义需要重新水合。

不得增加固定间隔轮询。Xur 低频到访 / 离开边界定时器继续保留。

## 3. 请求合并与竞态处理

- 多个事件短时间发生时，按账号、角色、商人详情范围和资料库版本合并请求。
- 切换商人继续使用短防抖，只读取最后停留的商人详情。
- 手动刷新使用后发请求优先，能够接管已有后台请求。
- 角色变化后旧角色快照立即退出可见状态，新角色加载期间不得静默保留旧库存。
- 请求失败时保留同角色、同商人的已有库存，并明确显示数据时间和失败状态。

## 4. 差异模型

- 使用稳定 Offer 身份和 API 返回的配置指纹比较新旧快照。
- 稳定身份至少包含账号、`characterId`、`vendorHash`、`vendorItemIndex` 和刷新边界。
- 区分新增、售卖配置变化、购买条件变化和下架。
- 成本变化作为购买条件变化的子原因记录。
- 定义重新水合但原始 Offer 未变化时，不误报为库存变化。

## 5. 变化表达

- 商人头部展示本次新增、变化和下架数量。
- 卡片用文字标记“新增”或“售卖配置已变化”，不能只使用颜色。
- 无变化时明确显示“库存无变化”。
- 玩家查看后可以清除本地新内容状态。
- 动态刷新通过礼貌级 live region 宣布一次摘要，不逐张卡片播报。

## 6. 持久化与性能

- 只保存最小 last-seen Offer 指纹、刷新边界和已查看状态。
- 不长期保存完整历史库存，不建立无限增长日志。
- 快速切换商人时只为最终停留项请求完整详情。
- 变化计算在刷新成功后执行，失败或取消的请求不能覆盖较新的快照。
- 相同或更旧的响应版本不能重建页面或生成重复差异。

## 7. 非目标

- 不增加每分钟、固定间隔或后台常驻轮询。
- 不保留完整商人库存历史浏览器。
- 不把游戏内随机池推测成当前 Offer 的确定配置。
- 不把定义文案变化误报为售卖配置变化。
- 不在本需求实现关注通知规则。

## 8. 验收标准

- 切换商人时只刷新最后停留的商人。
- 同一销售位置的 API 配置发生变化时显示“售卖配置已变化”。
- 新增、变化和下架数量准确，无变化时显示无变化。
- 账号页切换角色不会显示旧角色差异或旧库存。
- Xur 到访 / 离开边界仍能触发必要刷新。
- 重复进入商人页不会因为相同快照重复产生“新增”状态。
- 快速事件并发时，较旧响应不会覆盖较新结果。

## 9. 待细化问题

- 进入商人菜单是否始终发起后台校验，还是缓存未过期时直接复用。
- 应用恢复前台时如何用 `nextRefreshAt` 和缓存边界避免重复请求。
- 变化标记保留到玩家查看、下一次刷新，还是固定时间后自动消失。
- 材料余额变化是否只更新可负担状态，还是进入差异摘要。

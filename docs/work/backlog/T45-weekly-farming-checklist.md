# T45：本周刷取清单

> 状态：🟠 首版开发完成，待真实账号验收
> 优先级：P1
> 类型：轮换装备决策 + 账号实例核对
> 建议入口：资料库中的“本周刷取”视图
> 关联能力：T20 武器推荐与仓库整理、T44 光等提升路线

## 1. 一句话说明

让玩家直接知道：本周轮换活动里哪些武器值得刷、推荐什么 Roll、账号里是否已经有合格实例，以及红框还差多少。

T45 回答“为了获得值得使用或可制作的装备，本周刷什么”；T44 回答“为了提高光等，先做哪个强力或巅峰奖励”。两项需求保持独立，但后续可以在统一的“刷什么”体验中互相跳转。

## 2. 玩家要解决的问题

现在玩家需要分别查看轮换信息、活动掉落表、多个推荐来源、仓库实例和游戏内红框进度，才能决定某个活动是否值得继续刷。

T45 要把这些事实合并成一个可执行结论：

- 当前有哪些突袭、地牢或异域任务正在轮换。
- 每个活动有哪些已确认的武器掉落。
- 哪些武器被可靠推荐来源评价为值得刷。
- 推荐来源分别要求哪些 Perk 或完整组合。
- 账号当前持有多少个同版本实例，最佳实例匹配到什么程度。
- 武器是否可制作，红框进度是多少，还差多少。
- 玩家现在应该“继续刷”“补红框”“已有合格 Roll”还是“信息不足，暂不能判断”。

## 3. 与现有需求的边界

### 3.1 复用 T20，不重新实现推荐系统

- 武器评价、推荐来源、Perk 要求、DIM 完整组合和实例 Roll 匹配全部复用 T20 的正式结果。
- T45 不建立第二套推荐数据库，不重新解释来源规则，也不把多个来源拼成虚假的统一 Roll。
- 推荐摘要与装备详情、仓库卡片必须使用同一份匹配结果。

### 3.2 不合并 T44

- T44 根据角色光等、掉落基准和强力/巅峰奖励判断“怎样提高光等”。
- T45 根据轮换掉落池、推荐数据、账号实例和制作进度判断“怎样获得想要的装备”。
- 两者可以共享活动身份、轮换时间和奖励来源，但不共享价值判断、完成条件和排序规则。

### 3.3 不复制完整活动百科

T45 只展示本周实际轮换且存在可靠掉落依据的活动与装备，不维护攻略流程、机制教学、全历史掉落百科或固定周期推算。

## 4. 页面设计

### 4.1 页面位置

- 第一阶段放在资料库菜单中的“本周刷取”同级视图，复用装备资料、来源详情、推荐 Roll 和账号实例能力。
- 首页不展示完整刷取清单；后续只有在真实验收证明有价值时，才考虑一条紧凑摘要入口。
- T44 继续位于账号相关的光等成长区域，两边通过明确链接跳转到对应活动或装备。

### 4.2 活动摘要

每个活动首先显示一行可扫描摘要：

```text
守望者尖塔
本周轮换 · 6 天后结束
6 把武器 · 2 把值得刷 · 1 把红框未完成
```

活动摘要必须说明：

- 活动类型和正式名称。
- 当前是否处于可重复刷取或本周轮换状态。
- 结束时间或下一次重置时间。
- 已确认武器数量。
- 值得继续刷、红框未完成和信息不足的数量。

活动折叠时仍保留这些结论，不能要求玩家展开所有武器后自行统计。

### 4.3 武器摘要

每把武器使用紧凑对象行或对象卡，首层只显示做决定需要的内容：

```text
武器名称 · 武器类型
推荐：Aegis S · 另有 2 个来源
红框：3 / 5 · 当前持有 4 把 · 最佳实例核心 Perk 4 / 5
结论：继续补红框
```

首层结论允许以下状态：

- `值得刷`：存在可靠推荐，账号没有满足条件的实例。
- `继续补红框`：制作图样尚未完成，并且该武器仍有明确刷取价值。
- `已有合格 Roll`：至少一个实例满足当前选择来源的核心要求。
- `当前已满足`：制作目标和实例目标均达到系统可确认条件。
- `信息不足`：掉落、推荐、实例配置或制作进度缺少可靠数据。

不能使用裸复选框表达“毕业”。系统判断与玩家个人决定必须分开：

- 系统状态只根据已确认事实显示“当前已满足”或“仍有缺口”。
- 如后续增加个人规划，使用明确操作“标记为不再刷”，保存为可撤销的本地偏好，不伪装成系统事实。

### 4.4 展开详情

玩家展开单把武器后，按以下顺序显示：

1. **为什么值得刷**：各推荐来源的等级、结论和必要备注；先显示摘要，详细来源证据按需展开。
2. **推荐 Roll**：各来源独立展示枪管、弹匣、主要 Perk、大师属性和起源特性；不跨来源拼接。
3. **当前已有**：同一正式发布版本的真实实例按匹配程度排序，第一项明确标记为“当前最佳”。
4. **制作进度**：显示 `3 / 5`、还差 `2` 个；不可确认时显示原因，不展示伪造的 `0 / 5`。
5. **获取依据**：显示活动掉落数据的来源、版本和确认时间，可跳转统一装备详情。

## 5. 数据来源与可实现性

### 5.1 本周轮换

- 优先使用 Bungie CharacterActivities、Milestones、活动 Definition 和当前已有的首页轮换资源确认活动身份与状态。
- 不根据固定周序、中文名称或第三方网页正文直接推算当前轮换。
- 轮换状态无法确认时，活动不得显示为“本周可刷”。

### 5.2 活动掉落池

这是 T45 开发前必须解决的最大前置问题。

- Bungie Manifest 未必提供完整、实时且可追溯的活动掉落表。
- 必须调研可机器读取、允许使用、能够维护版本和更新时间的外部或社区数据源。
- 每条活动—装备关系要保留来源、数据版本和确认时间。
- 没有可靠来源时显示“掉落池暂不可确认”，不能根据装备描述、来源文案或名称关键词猜测。

### 5.3 武器推荐和账号实例

- 推荐结论直接消费 T20 的人工来源与 DIM Wishlist 结果。
- 当前持有实例来自共享账号快照，按 canonical 发布版本身份匹配；不同发布版本不得混为同一把。
- 实例位置、锁定和 Roll 更新遵守共享账号同步与写后更新规则，不建立资料库私有账号缓存。

### 5.4 红框与制作进度

- 开发前确认 Bungie ProfileRecords、PresentationNodes、Collectibles、Plug/Objectives 与制作图样 Definition 的最小可靠关系。
- 只展示 Bungie 当前账号真实返回的制作进度。
- 已完成、不可制作、进度隐藏和接口未返回必须是不同状态。
- 红框资源独立异步加载，失败不能阻塞轮换清单、推荐数据和账号实例。

## 6. 排序规则

活动先按当前可刷状态、结束时间和稳定活动 Hash 排序，不按本地化名称排序。

活动内武器按以下优先级排序：

1. 红框未完成且存在可靠推荐。
2. 没有合格实例且存在可靠推荐。
3. 已有合格实例但制作尚未完成。
4. 当前已满足。
5. 信息不足或没有推荐覆盖。

同一服务器数据、同一推荐版本和同一账号快照在两台设备上的系统排序必须一致。玩家本地“标记为不再刷”若未实现跨设备同步，不得影响服务器事实排序。

## 7. 加载、缓存和失败

- 轮换、掉落池、推荐匹配、账号实例和制作进度保持独立资源状态，不做一个巨型阻塞请求。
- 首屏先显示已确认的活动和装备身份，推荐、实例与红框状态在各自区域补齐。
- 刷新期间保留上一份已确认结果，并明确显示对应资源正在更新。
- 某个推荐来源失败只影响该来源；红框读取失败不能把已有实例显示成 0。
- 切换活动或展开武器不触发页面轮询；使用现有账号、资料库和轮换事件驱动更新。
- 缓存必须带活动身份、资料库版本、推荐 revision、账号 Profile 时间和算法版本，不能跨版本复用旧结论。

## 8. 响应式与操作

- 宽屏使用活动分组和紧凑装备行；窄屏改为单列，不保留横向大表格。
- 首层不直接铺开多个推荐来源表格；详细证据由玩家展开。
- 活动和武器使用稳定键盘焦点顺序，展开后焦点进入详情，收起或关闭后返回来源项。
- 状态必须同时使用文字与颜色，不能只用绿色、黄色或复选框表达。
- 长 Perk 名称和多来源内容允许换行或内部滚动，不使用固定宽度截断关键信息。

## 9. 实现切片

1. **数据源调研**：确认轮换身份、活动掉落池与制作图样进度的可靠来源、许可、更新频率和失败语义。
2. **领域模型**：建立活动、掉落关系、刷取价值、账号满足状态和证据引用的纯领域模型。
3. **资源编排**：组合轮换、掉落池、T20 推荐、共享账号快照和独立制作进度资源。
4. **资料库 ViewModel**：输出活动摘要、武器排序、状态原因、来源证据和部分失败状态。
5. **共享 UI**：在 `packages/ui/src/library/` 增加“本周刷取”视图，Desktop/Web 只接 adapter。
6. **真实账号验收**：核对当前轮换、完整掉落池、推荐来源、账号实例、最佳 Roll 和游戏内制作进度。

## 10. 验收标准

### 数据正确性

- 当前轮换活动与 Destiny 2 实际状态一致，不使用固定周序猜测。
- 展示的每件掉落装备都能追溯到明确数据源和版本；无法确认时不冒充完整掉落池。
- 推荐等级、Perk 要求和实例匹配与 T20 的装备详情及仓库结果一致。
- 当前持有数量、版本和最佳实例与共享账号快照一致。
- 可制作状态和红框进度与游戏内一致，缺失数据不显示为 0。

### 玩家感知

- 玩家不展开详情也能看懂本周有哪些活动、哪些武器值得刷以及当前主要缺口。
- 玩家能从单把武器进入来源评价、推荐 Roll、当前最佳实例和制作进度。
- 页面直接说明“为什么继续刷”或“为什么当前已满足”，不要求玩家自己比较三张表。
- “系统已满足”和“玩家不再刷”有明确区别，不使用含义不明的复选框。

### 架构与性能

- T45 不复制 T20 推荐与匹配逻辑，不建立资料库私有账号快照。
- 掉落池或红框资源失败不会阻塞资料库搜索、装备详情、账号页或首页。
- 页面没有定时轮询；更新由资料库、账号和轮换资源事件驱动。
- Web 与 Desktop 使用同一个 `packages/ui` 页面实现，平台壳不复制产品 UI。

## 11. 非目标

- 不负责 T44 的强力、巅峰或光等提升排序。
- 不提供活动攻略、机制教学、队伍招募或自动匹配。
- 不自动分解、装备、转移、锁定或领取奖励。
- 不承诺某次活动必定掉落指定武器或指定 Perk。
- 不根据玩家持有数量自动删除实例，也不替玩家决定主观毕业标准。
- 不在首页恢复常驻的大型任务或刷取清单。

## 12. 开发前置结论

T45 不等待一个能够包办全部事实的单一数据源。正式功能开发前需要完成两项工程前置：

1. 建立带证据、版本、许可和校验规则的 `activity-loot.v1` 受控掉落关系数据集，并录入首批当前轮换突袭 / 地牢。
2. 用真实账号验证图样 Record 映射在已完成、未完成、不可制作和字段缺失状态下的表现。

如果只能确认轮换活动，无法确认某件装备的掉落关系或图样状态，页面必须显示“信息不足 / 无法确认”，不能把活动轮换入口包装成完整 T45。

## 13. 落地调研结论（2026-09-10）

### 13.1 结论先说

T45 可以实现，但不能把“Bungie 当前返回的活动奖励”直接当成完整掉落池。

- 本周轮换、活动身份、挑战进度和奖励等级：可以使用 Bungie 实时 Profile / Public Milestones 与当前 Manifest。
- 武器是否属于某个活动的候选来源：可以使用 Manifest `DestinyCollectibleDefinition.sourceHash/sourceString`，并参考 DIM 的 D2AI 来源映射。
- 某次突袭或地牢的完整武器—遭遇战掉落表：Bungie 没有提供一个稳定、完整、可直接查询的公开接口，必须使用应用自己维护的受控数据集。
- 制作图样进度：可以使用 Manifest 中 `completionInfo.toastStyle = CraftingRecipeUnlocked` 的 Record，加上 Bungie Profile `Records` 的 Objective 进度。

因此首版应采用“实时事实与静态关系分层”方案，而不是继续寻找一个不存在的单一 API。

### 13.2 已核实的数据能力

| 事实 | 可用来源 | 核实结果 | 允许的用途 |
|---|---|---|---|
| 当前轮换活动 | Bungie `CharacterActivities`、`Public Milestones`、活动 Manifest | 当前账号样本能返回轮换突袭 / 地牢及角色挑战 | 判断本周活动身份、开放窗口和角色完成状态 |
| 周挑战奖励等级 | 活动挑战的 `displayRewards[].itemQuantity`，旧定义兼容 `dummyRewards` | T44 已验证；可区分“强力装备 / 突袭装备”等奖励定义 | 只用于 T44 提光路线，不用于武器掉落池 |
| 装备活动来源候选 | Manifest `DestinyCollectibleDefinition.sourceHash/sourceString` | 当前 Manifest 中突袭 / 地牢武器可解析到活动来源；装备定义自身 `sourceData` 当前为空 | 生成活动级候选装备，并作为掉落证据之一 |
| 图样身份 | Manifest `DestinyRecordDefinition.completionInfo.toastStyle = 8` 与同名武器定义的 `inventory.recipeItemHash` | 当前版本 183 条图样 Record 与 183 个可制作输出能按名称一一对应；仍需保留 Hash 级校验 | 找到武器图样 Record 和制作模板 |
| 图样进度 | Bungie Profile `Records.data.records[recordHash].objectives[]` | 真实样本出现 `0/5`、`2/5`、`5/5`、`1/2` 等进度；`state` 可区分未完成、已完成、不可用等位 | 展示红框 / 图样进度，缺失时显示“无法确认” |
| 账号实例与 Roll | 共享 `AccountSnapshot`、T20 推荐匹配结果 | 已有正式版本匹配与七类状态 | 生成“继续刷 / 已有合格 Roll / 当前已满足” |

### 13.3 掉落池数据源评估

#### A. Bungie Manifest / API：权威但不完整

Manifest 的 `DestinyCollectibleDefinition.sourceHash/sourceString` 能回答“这个物品通常来自哪个来源”，但不能回答：

- 每个遭遇战具体掉哪些武器；
- 普通宝箱、隐藏宝箱、挑战宝箱的差异；
- 专家 / 普通、复刻 / 原版、特殊掉落条件；
- 某个活动当前是否仍能重复获取。

Manifest 的 `DestinyActivityDefinition.rewards`、挑战 `displayRewards` 也不是完整武器掉落表。T44 已经证明，`visibleRewards` 可能混入普通掉落或展示奖励，不能复用为 T45 掉落池。

#### B. DIM / d2-additional-info：适合作为来源候选和维护参考

本地 DIM 的 `source-info-v2.ts` 明确是由 D2AI 构建生成，不应手工修改。DIM 使用活动 `sourceHash` 与 `itemHashes` 维护来源候选，仓库与 DIM 本身采用 MIT License；`d2-additional-info` 也采用 MIT License。

它适合用于：

- 活动级来源候选；
- 版本 / 复刻装备的 Hash 参考；
- 新 Manifest 发布后的差异核对。

它不包含 T45 所需的完整“遭遇战 → 掉落物”关系，因此不能单独作为完整掉落池。

#### C. Felicity 等社区项目：有完整表，但不能直接复制

本地调研到 Felicity 的 `LootTables.cs`，它采用手工维护的活动、遭遇战和物品 Hash 表，能证明“完整遭遇战掉落表”需要维护关系数据，而不是从 Bungie 运行时推导。

该项目使用 AGPL-3.0，且其数据维护与本项目许可、来源链不一致。因此 T45 不直接复制代码或表；最多作为人工交叉核对材料。没有明确许可的网页、攻略站和在线表格同样不作为运行时依赖或直接 vendoring 来源。

### 13.4 推荐的正式数据集

新增一个由本项目维护的 `activity-loot` 数据集（落在 services / community 数据边界，不写进 UI）：

```text
activity-loot.v1
  activity_hash
  activity_name_key
  activity_kind: raid | dungeon | exotic_mission
  encounter_key
  encounter_label
  item_hash
  item_variant: normal | adept | timelost | reprised | other
  drop_scope: encounter | final_chest | secret_chest | challenge | activity
  source_kind: curated | bungie_collectible_crosscheck | community_crosscheck
  source_url
  source_license
  evidence_note
  manifest_version
  verified_at
  enabled
```

硬规则：

1. 只有 `curated` 且有 `verified_at` 的关系，才能进入“已确认掉落池”。
2. 只有活动级来源、没有遭遇战证据的装备，显示为“活动来源候选”，不能混入完整掉落池数量。
3. 当前 Manifest 找不到 `item_hash` 时，关系标记为过期，不静默替换同名物品。
4. 普通版、专家版、复刻版使用独立 Hash；不能按中文名称合并。
5. 数据集本身带 revision、Manifest 版本和证据时间；客户端只缓存结果，不修改关系真相。

首版建议只收录当前轮换突袭和地牢的武器，并按遭遇战维护；异域任务、护甲、隐藏宝箱和跨活动来源作为后续扩展。

### 13.5 图样进度正式实现口径

图样不要以“账号有几把红框武器”代替。正式顺序应为：

1. 从武器 canonical Hash 找到 `inventory.recipeItemHash`，确认它是可制作输出。
2. 通过 Manifest Record 的 `toastStyle=CraftingRecipeUnlocked` 和规范名称找到图样 Record。
3. 优先读取账号 `ProfileRecords`；Record 为角色范围时再读取各角色 `CharacterRecords`，取已返回且语义有效的记录。
4. 读取 Record 的可见 Objective，使用 `progress / completionValue` 展示进度。
5. `ObjectiveNotCompleted` 或 Objective 未完成：显示“还差 N 个”；已完成且未被 `RewardUnavailable` / `Obscured` 等状态阻塞：显示“已完成”。
6. Record、Objective 或映射缺失：显示“制作进度无法确认”，绝不显示 `0/N`。

当前 DIM 的做法可作为参考：先用 `recipeItemHash` 判断可制作，再通过 `CraftingRecipeUnlocked` Record 与武器名称匹配；但 T45 应额外保存 canonical Hash、映射证据和多版本冲突状态，不能只依赖裸名称。

### 13.6 刷新与缓存合同

T45 至少有五份资源，必须分开刷新和显示状态：

| 资源 | 真相 | 刷新触发 | 缓存键 |
|---|---|---|---|
| 轮换 | Bungie 实时活动 / 里程碑 | 每周窗口、手动刷新、账号事件 | Bungie Profile / period key |
| 掉落关系 | `activity-loot` 受控数据集 | Manifest 更新、数据集 revision 更新 | activity hash + manifest version + dataset revision |
| 推荐 | T20 | 推荐库 revision 更新 | item hash + recommendation revision |
| 账号实例 | 共享 AccountSession | 账号同步、写后局部 patch | account + profile minted timestamp |
| 图样进度 | Bungie Records | 账号同步、展开详情时按需读取 | account + profile minted timestamp + record hash |

页面刷新不应把五份资源伪装成一个瞬时完成的请求。首屏可先显示活动和掉落关系；推荐、实例和图样独立补齐。任一资源失败只显示该资源的错误和旧数据，不清空其他已确认结果。

### 13.7 首版可交付范围

首版可以承诺：

- 当前轮换突袭 / 地牢；
- 受控数据集已覆盖的活动级武器来源；
- T20 推荐状态；
- 账号内同一 canonical 版本的实例与最佳匹配；
- 可确认的图样进度；
- 每条结论的来源、版本和更新时间。

首版不能承诺：

- 自动从 Bungie 推导完整掉落池；
- 所有活动、所有异域任务和所有隐藏宝箱；
- 没有证据时的“完整掉落数量”；
- 仅凭同名判断复刻版、专家版或旧版已经满足。

### 13.8 调研后的开发闸门

以下开发闸门已于首版实现中完成：

1. 已建立 `activity-loot.v1` 类型合同、来源许可、固定 commit 证据和运行时结构校验。
2. 已录入 2026-09-10 当前轮换的门徒誓约、救赎的边缘、贪婪之握和战争领主的废墟；首版只承诺活动级来源，不冒充遭遇战掉落表。
3. 已接入 Profile Records 图样解析，代码区分已完成、进行中、不可制作、隐藏、未返回、未拥有权限和读取失败。
4. 已完成领域决策、Desktop 资源编排、T20 复用、共享账号实例核对和 `packages/ui/src/library/` 页面。

真实账号验收仍是发布前门槛，不能仅凭代码状态宣称图样映射与游戏内完全一致。

## 14. 首版实现结果（2026-09-10）

### 14.1 玩家入口与感知

- 资料库新增第三个同级 Tab“本周刷取”；装备搜索、Perk 搜索和本周判断互不混淆。
- 左侧直接显示建议继续刷、图样有缺口、已有合格结果和已核对装备数量，并显示周重置、本次读取和数据集 revision。
- 右侧按轮换活动分组，单件装备首层显示推荐覆盖、图样进度、账号持有、当前最佳实例和“继续补图样 / 值得继续刷 / 已有合格 Roll / 当前已满足 / 信息不足”结论。
- 单件可进入统一装备详情；优先打开当前最佳真实实例，没有实例时打开该装备的资料库定义。
- 未覆盖活动明确显示“轮换已确认，掉落关系尚未核对”，不会显示空白列表或猜测结果。

### 14.2 数据与状态合同

- 当前轮换继续复用首页 `weeklySummary`，不新增固定周序或第二份轮换请求。
- `activity-loot.v1` 当前关系来自 Bungie Manifest `sourceHash`，并用固定到 DIM commit `2a115690fd20717c4a8daa185eccd027226d4832` 的 MIT 来源索引交叉核对。
- 图样进度由 Desktop 读取 Bungie Profile Records 组件 `900`；缺失或失败不会伪造成 `0/N`。
- 推荐定义与实例 Roll 完全复用 T20；账号实例来自共享账号 Store，不建立资料库私有账号缓存。
- 推荐实例扫描尚未完成时，已有实例不会被误判为“没有合格 Roll”；页面降级为“信息不足”。
- 普通版、专家版、复刻版继续按装备 Hash 区分；首版不展示无法可靠确认的专家版掉落。

### 14.3 刷新与失败

- 进入“本周刷取”后按需加载；切换其他资料库 Tab 不发起轮询。
- 页面把刷新拆成“刷新本周轮换”和“重新核对图样与推荐”；前者强制刷新共享首页简报，后者强制刷新 Bungie 图样记录并重新核对 T20，避免一个按钮伪装成全部资源已经同步。
- 更新期间保留上一份已确认清单，并持续显示更新状态。
- 轮换 / 图样读取错误与 T20 推荐错误分开显示；推荐失败不会清空活动、账号持有或图样事实。
- 新请求会淘汰旧请求结果，避免轮换变化或连续点击后由较慢旧响应覆盖新清单。

### 14.4 待验收清单

1. 打开“资料库 → 本周刷取”，核对四个轮换活动与游戏内本周轮换一致。
2. 抽查每个活动至少两件装备，确认名称、版本和活动来源正确；当前只验收活动级归属，不验收具体遭遇战。
3. 找一件图样进行中的武器，核对 `进度 / 总数` 与游戏内一致。
4. 找一件已完成图样和一件不可制作武器，确认分别显示“图样已完成”和“不可制作”，不会显示 `0/N`。
5. 对账号已有实例的武器，核对持有数量、位置和当前最佳实例；打开详情后与仓库 T20 结论一致。
6. 分别点击“刷新本周轮换”和“重新核对图样与推荐”，确认各自显示进行中状态，旧内容保持可见，完成后读取时间与结论更新。
7. 在窄窗口检查页面回到单列；用键盘左右切换三个 Tab、上下移动装备操作按钮，焦点不会丢失。

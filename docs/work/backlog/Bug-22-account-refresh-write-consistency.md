# Bug #22：账号刷新与写后状态一致性

## 问题

账号、仓库、配装和首页账号摘要虽然已经共享 renderer Store，但 Profile、Session、Repository、持久化快照和写后状态同步之间没有统一的服务端版本协议。由此可能出现：

- 点击刷新后复用旧请求或旧缓存，页面没有变化却显示同步完成；
- 转移已在游戏内生效，页面先更新后又被旧 Profile 覆盖；
- 装备请求已被 Bungie 接受，但页面无法区分“同步中”和“已装备”；
- 两台电脑各自接受不同时间返回的 Profile，刷新后仍显示不同位置；
- 配装在仓库转移尚未进入 Bungie 角色背包时立即装备，产生 1623 / 1640；
- 首页“强制刷新”只扩大刷新范围，没有保证底层请求真正绕过缓存。

缓存本身不是问题。问题是各缓存层没有共同的版本水位线，而且普通写操作曾把接口成功错误地绑定到逐操作 Profile 轮询和完整账号刷新。

## 设计原则

### 1. Bungie Profile 是服务端真相，但只能按版本前进

- 保留 `responseMintedTimestamp`，并随 `AccountSummary` / `AccountSnapshot` 传递。
- Session、持久化快照和 renderer Store 都不得接受比当前水位线更旧的 Profile。
- 相同或更旧的 Profile 不得重建当前快照，不能用延迟响应覆盖接口成功后已经提交的本地局部状态。
- 快照构建完成时再次核对构建所依据的 Profile 版本，避免构建期间状态变化后提交旧结果。

### 2. 一个账号协调器负责所有账号装备状态

- 账号、仓库、配装和首页账号摘要只消费同一份账号快照。
- 页面只表达刷新意图；Session 决定缓存、单飞、强制升级、版本接受和持久化。
- 初始、定时、回到前台和手动同步必须经过同一个 Session，不能维护互不认识的 Profile 缓存。

### 3. 普通写操作以 Bungie 接口结果为完成边界

普通转移、锁定、装备和邮政官取回使用：

`submitting → accepted / failed`

- Bungie 接口明确成功后，Renderer 直接把返回的 `account_patch` 提交到共享 Store 的本地确认态，不再登记逐实例 Pending。
- 普通写操作不启动独立 `account-write-sync`，不进入顶部全局同步状态，也不因确认失败或超时触发完整账号刷新。
- 后续 10 分钟定时同步、回到前台补同步或玩家手动同步获得的新 Profile 负责自然校准；相同或旧 Profile 仍不得回退当前页面。
- 接口成功但缺少 `account_patch` 时只显示短提示，等待下一次正常账号同步，不立即构建和传输完整账号快照。

### 4. 配装步骤必须依赖真实前置状态

- 每一步执行前重新定位实例，避免使用点击时的旧位置。
- 从仓库转移后，必须确认实例已进入目标角色背包，再调用装备接口。
- 批量装备必须保持武器、护甲异域唯一性，并对 Bungie 返回的逐项状态做真实核对。
- 不以固定延迟代替状态确认；延迟只能作为重试节奏。

### 5. 强制刷新必须真正升级

- 普通后台请求进行中时，用户强制刷新不得直接复用普通请求。
- 应等待已有请求结束后再执行一轮强制请求，或将已有请求升级为强制请求。
- 首页情报的 `force` 必须传递到最底层 Bungie Request Broker。
- 页面保留旧内容，分别显示“刷新中”“已更新”“服务器版本未变化”“刷新失败，继续显示旧数据”。

## 诊断要求

每轮账号刷新至少记录：

- request ID、刷新原因、是否强制；
- 请求开始时 Store revision；
- Profile `responseMintedTimestamp`；
- 当前水位线；
- 接受、跳过或丢弃原因；
- 快照提交 revision 和来源；
- 当前前台写请求数量与最近一次局部 patch 应用结果。

每次普通写操作至少记录接口耗时、返回 patch 和本地应用结果；配装前置确认额外记录实例进入角色背包的读取结果。应用版本与 Electron 版本必须分开导出。

## 验收标准

- 游戏内移动装备后点击任意账号同步入口，账号、仓库、配装和首页账号摘要最终一致。
- 转移成功后页面立即显示目标位置和一次成功提示，不出现持续“同步中”；相同或旧 Profile 不能让装备跳回或消失。
- 单击刷新时，如果 Bungie 没有返回更新版本，明确显示“服务器版本未变化”，不能伪装成读取到新状态。
- 普通写操作完成后不再发起轻量 Profile 轮询或写后完整刷新；正常账号同步最终与游戏事实一致。
- 仓库转移后的装备步骤只有在服务器确认进入目标角色背包后执行。
- 两台电脑在分别执行强制同步并接受同一 Profile 版本后，实例位置一致。
- 首页强制刷新不会被启动后台请求或 TTL 缓存吞掉。

## 本次实现

- `AccountSummary` 保留 Bungie `responseMintedTimestamp`，Account Session 与 renderer Store 都拒绝旧 Profile；被拒绝的旧响应不再继续驱动页面提示、角色选择或仓库派生状态。
- Account Session 每次提交完整快照后都会通过主进程事件通知 Renderer；账号、仓库、配装和首页共享 Store 会消费同一份快照，不再出现主进程已落盘正确数据但页面仍停留在旧背包列表的分叉状态。
- 手动同步只有在 Renderer Store 真正接受返回快照后才显示完成；若响应因版本倒退被拒绝，会明确保留当前状态并报告本次结果未应用。
- Account Session 与 Renderer Store 都改为严格单调水位线：相同或更旧的 `responseMintedTimestamp` 不再重建完整快照。
- 账号页、仓库页、设置页、AI 空状态、首页和配装统一使用“同步装备数据”；设置概览不再重复执行同步，只导航到账号设置。“重新登录 Bungie”独立说明只用于登录失效、权限异常或切换账号。
- 初始、定时、回到前台和手动账号同步共用同一个 Account Session 请求协调器，避免两套互不认识的 Profile 请求互相覆盖。
- 启动只恢复上次账号快照，不由主进程静默远程刷新；Renderer 全局账号控制器负责本次运行唯一一次可见初始同步，页面挂载与切换菜单不触发账号刷新。
- 已删除共享 Shell 与账号控制器之间重复的初始同步触发；登录流程和已授权启动均只进入同一个账号刷新协调器。
- 攻略和助手 IPC 只读取当前全局账号快照；配装执行前后的复核必须使用全局账号控制器，已移除功能 Hook 内直接强刷账号 API 的 fallback，避免 Session 与 Renderer Store 出现两套刷新所有者。
- Repository 与 Session 的账号 TTL/SWR 已移除；手动同步始终作为权威请求穿透普通缓存，并以 Profile 水位线原子提交中央账号 Store。
- 转移、锁定、装备、邮政官取回和普通配装在 Bungie 返回成功后直接提交共享 Store 的局部确认态；账号、仓库、配装和首页同时看到同一结果，不再登记逐实例 Pending。
- 普通写操作不再调用 `startAccountWriteVerification`，因此不会创建五轮 Profile 退避任务、75 秒 Renderer 兜底或异常终态完整账号刷新。
- 单件装备、批量装备和最高光等的成功 patch 都立即提交；接口成功但未返回 patch 的少数兼容路径只提示等待下一次正常账号同步。
- 账号状态对超过 90 秒的 `profile_minted_at` 显示“游戏数据延迟”，不再使用本地请求完成时间冒充游戏数据新鲜度。
- 最高光等和配装从仓库取出装备后，先读取真实角色 inventory / equipment，确认实例到达目标角色后才调用装备接口，避免转移尚未同步时产生 1623 / 1640。
- 首页 force 请求遇到普通 in-flight 时会排队追加真正的强制请求，并把 force 传递到最底层 Request Broker；移除 Home Session 外层重复缓存造成的强制刷新失效。
- 手动同步会清除已经结束的写操作提示，并以新 Profile 校准本地局部状态。
- 推荐核对在账号快照原子提交后异步启动，不阻塞账号、仓库和配装更新；账号位置变化直接复用实例匹配缓存，Roll 变化只重算对应实例。
- 诊断导出的应用版本优先读取产品 package version，不再把 Electron 版本误报为 d2-tools 版本。
- 普通写操作不再占用跨菜单账号同步状态；顶部、页面横幅和任务 Dock 不展示写后确认进度，只保留当前按钮提交状态与一次操作结果。

## 待真实账号验收

- 游戏内把仓库物品转到角色后手动同步，确认账号、仓库和配装同时显示同一实例位置。
- 在应用内转移物品，确认 Bungie 接口成功后页面立即移动对应实例且不显示持续“同步中”；随后正常同步与游戏一致。
- 使用包含仓库装备的最高光等或一键配装，确认物品进入角色背包后才装备，“浮游孢子”不再因转移时序产生 1640。
- 两台电脑分别强制同步，比较诊断中的 Profile 版本和实例位置，确认最终一致。
- 首页启动后台刷新期间点击手动刷新，确认后台请求结束后仍追加一次强制刷新。

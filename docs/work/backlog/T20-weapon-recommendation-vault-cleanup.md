## 1. 目标与边界

仓库页帮助玩家完成四件事：

1. 判断一把武器是否符合某个推荐来源。
2. 在同名武器之间优先比较 Perk 1 与 Perk 2。
3. 保护锁定、配装引用、玩家手动保留和无法安全判断的实例。
4. 由玩家确认锁定、标记或转移，最终分解仍在游戏内完成。

仓库首层必须直接展示玩家工作流，而不是先展示核对统计和数据源细节：

```text
1 浏览装备
  → 2 看推荐：选择来源 → 核心 Perk x/y → 完整 x/y；DIM 看最佳组合 x/y
  → 3 整理同名：重点比较 Perk 1 与 Perk 2
  → 玩家显式标记、锁定或转移
  → 游戏内完成最终分解
```

账号同步是这条流程的前置状态，不是额外工作区。正常时只显示“已同步时间”；未同步、同步中或失败时才显示可执行提示。

应用不得自动生成“应该分解”的结论，不得自动锁定、解锁、保留、转移或分解。

## 3. 推荐数据与匹配

### 3.1 两条数据链

应用展示五个来源，但底层必须分开：

```text
Aegis / LGpig / YXCRALLXY / Sayalarry
  → 31 列严格 CSV
  → Manifest 语义校验
  → 人工来源 SQLite

DIM 社区愿望单
  → 原生 itemHash + perkHash 组合
  → 原生解析与诊断
  → DIM SQLite

两条数据链
  → 按 instanceId 核对玩家实际 Roll
```

DIM Wishlist 来自 GitHub 或玩家本地导入，与 `dim-api` 的 DIM Sync 服务无关。

### 3.2 导入格式与严格语义

普通玩家使用简表导入，不要求填写采集证据或 Manifest 展示字段：

```text
武器 / 武器ID（可选） / 英文名称（可选） / 推荐来源 / 用途
第一列 / 第二列 / Perk 1 / Perk 2 / 大师 / 起源特性 / 评级 / 备注
```

应用根据武器名称或 ID 读取当前 Manifest，自动确认官方武器身份并补齐武器 ID、分类、图标和来源信息；英文名称可以留空，不参与中文简表的必要校验。当前 31 列格式保留为 T20 完整数据包和旧版本兼容格式，不作为普通玩家模板；DIM Wishlist 继续使用独立文件和独立数据链。

来源管理中同时提供“导出玩家模板”和“导出当前推荐”：前者生成空白简表，后者把当前人工来源转换为简表，便于玩家修改后再导入；完整 31 列证据数据不进入普通导出。玩家简表固定执行合并更新，只新增或更新对应来源与武器规则，不删除文件中未出现的已有推荐；只有无异常的 31 列维护者完整包执行整体替换。任一格式存在异常行时只忽略对应行，其余有效行合并导入，已有正确规则继续保留。

### 3.3 严格语义

人工来源的武器、第一列、第二列、大师、Perk 1、Perk 2 和起源特性只接受：

1. 官方 Hash 精确命中；或
2. 规范化后的 Bungie 官方全名完全相同。

人工来源简表或完整 CSV 的来源身份只接受 Aegis、LGpig、YXCRALLXY 和 Sayalarry；未知来源按行忽略，DIM 行不进入人工链。武器 ID 可在简表中留空，应用先按官方中文名称解析；名称无法唯一核对时才要求补充 ID。

禁止：

- `contains`、前后缀和“候选唯一”包含匹配。
- 简称、旧译、同义词和人工推断。
- 大师属性词干归类，例如“填装/装填”“操控/操控性”。
- 自动把“伤害”改成“冲击”。
- 无法证明时忽略错误并继续激活。

维护者生成器可以在写出 CSV 前依据明确的来源术语表完成一次性官方化，例如将来源中的“换弹”写成 Manifest 官方名称“填装速度”；导入器本身仍不接受简称或自动推断。所有严格栏位最终只允许写入已由当前 Manifest 精确确认的名称，已划除、已删除或无法确认的附加项只保留在来源证据中，不得从原始展示字段回填。

存在任一阻塞项时不得激活新人工来源数据。导入确认必须重新核对 CSV 指纹和 Manifest，并使用单事务整体替换。

### 3.4 DIM 原生规则

- 一条 DIM 规则保存一个完整 Hash 组合，组合内全部必需，多条组合任选其一。
- 不转成普通六栏计数，不跨组合累计 Perk。
- 同栏多个必需项、缺栏、特殊异域插槽和无法归栏 Hash 保留原始结构。
- 旧 Hash 只有在官方身份能够精确证明时才映射。
- 无法确认时显示“该 DIM 规则无法核对”，不能判定为未符合。
- 在线更新固定到准确 commit；网络失败继续使用上一次成功 revision。

### 3.5 旧 SQLite

新 schema 至少记录：

```text
semantic_validation_version
validated_manifest_version
人工来源 CSV 指纹
DIM revision 与原文件指纹
数据集激活状态
```

缺少当前语义标记的人工来源库固定为 `unverified`。旧文件可以保留供回退或人工查看，但不参与核心状态、排序、保护或留拆判断。新数据全量通过后才整体替换；不得自动修正旧库中的“伤害”等历史值。

### 3.6 核心 Roll

人工来源最多核对六项：

```text
Perk 1 / Perk 2
  > 第一列 / 第二列
  > 大师 / 起源特性
```

同一栏多个候选为“任选其一”，不同栏之间为“全部必须分别核对”。`x/y` 中的 `y` 是来源明确要求的栏位数，不是候选 Perk 数；`x/y` 只表示六项事实符合度，不是评分。

| 状态 | 含义 | 玩家文案 |
|---|---|---|
| `full` | 全部明确要求均符合 | 全部符合 |
| `core` | 至少要求一个核心 Perk，所有已要求的核心栏均符合，但其他栏位有缺失 | 核心符合 |
| `close` | 来源未要求核心 Perk，非核心要求部分符合 | 接近推荐 |
| `key_missing` | 来源要求的任一核心 Perk 栏不符合 | 关键缺失 |
| `not_matched` | 来源有明确要求，但当前实例一项也未符合 | 未符合 |
| `weapon_only` | 来源只推荐武器身份 | 仅推荐这把武器 |
| `uncheckable` | 实例或规则无法安全核对 | 无法判断 |

以上七种只用于单来源汇总和排序，不直接作为每个栏位的玩家文案。仓库卡片、同名 Roll 对比与详情逐栏统一使用以下 4 种事实：

| 逐栏状态 | 判定 | 玩家文案 |
|---|---|---|
| `match` | 本件拥有项按 Hash 或规范化官方名称命中任一来源候选 | 符合 |
| `different` | 目标栏数据完整但没有命中；或整件 Roll 完整但当前版本没有该栏位 | 不符 |
| `uncheckable` | 整件 Roll 未读取、目标栏确实不完整，或来源要求完全没有可比较名称与 Hash | 无法判断 |
| `source_not_specified` | 来源没有要求该栏位 | 来源未要求 |

来源名称没有解析出当前武器版本的 Hash，不能单独把完整本件数据覆盖为 `uncheckable`。只要来源仍有可比较的官方名称，且本件目标栏完整，就必须按名称继续判定为“符合”或“不符”。整件 Roll 完整但当前版本不存在目标栏时，结果为“不符”，详情补充“本版本无此栏位”。

单来源判定固定按以下优先级执行：

```text
存在无法确认的必需栏位 → uncheckable
没有任何栏位要求       → weapon_only
全部必需栏位符合       → full
任一已要求核心栏不符   → key_missing
核心栏全部符合         → core
无核心要求且部分符合   → close
其余                   → not_matched
```

只要求 Perk 1 或只要求 Perk 2 时，该单栏就是完整核心要求；不能因为没有“双核心”而降为 `close`。来源未要求 Perk 1/2 时，不得凭第一列、第二列、大师或起源特性伪造“核心符合”。

DIM 不使用六项权重。任一完整组合符合即为符合；没有组合符合时，优先显示可核对组合中的最接近结果；若仍存在可能符合但无法核对的组合，则显示无法核对，不能判为未符合。

推荐按武器身份共享，但每个 `instanceId` 必须使用自身实际拥有 Roll 独立计算。Manifest 可掉落池不得冒充实例 Roll。

多个来源始终独立保存结果，不跨来源累计 `x/y`。推荐列表只显示 5 类玩家结果：

- `符合推荐`：至少一个来源为 `full / core` 或 DIM 完整组合符合，且没有同用途的明确冲突。
- `部分符合`：存在正向符合与明确不符的来源冲突，或只有 `close / weapon_only` 等部分证据。
- `未符合`：有来源覆盖，所有可核对来源均未符合。
- `无法判断`：任一来源因本件 Roll 或规则本身缺少真实可比较数据而无法判断；安全原因优先显示。
- `无推荐`：没有任何启用来源覆盖。

`general` 与 PVE、PVP 都视为用途重叠；PVE 与 PVP 之间不直接构成来源冲突。首层存在多个来源时只显示结论和来源数量，不用固定来源顺序伪造权威高低；全部来源进入“查看依据”。

DIM 与四个人工来源使用同一用途冲突规则：DIM 完整组合符合与人工来源关键不符，或人工来源核心符合与 DIM 明确不符，只要用途重叠就在推荐列表显示“部分符合”。DIM 同一来源内部的多条组合仍是任选其一，不互相制造冲突。

强制保护包括：游戏内锁定、精确配装引用、玩家手动保留、独特 Roll、来源冲突、数据不完整、推荐库未覆盖或未验证。

### 3.7 来源管理与纠错

推荐数据必须允许玩家纠错，但不能直接破坏发布方原始数据。管理入口分为三个层级：

| 层级 | 玩家操作 | 生效范围 | 恢复方式 |
|---|---|---|---|
| 单条规则 | 移除某把武器下某来源的一条推荐 | 只停止该规则参与匹配、排序、推荐保护和批量整理 | 在“已移除规则”中恢复 |
| 整个来源 | 停用或移除 Aegis、LGpig、YXCRALLXY、Sayalarry 或 DIM | 该来源全部规则停止参与结论，其他来源继续工作 | 停用可直接启用；移除需重新导入或更新后显式恢复 |
| 当前数据集 | 删除当前人工推荐数据或移除当前 DIM Wishlist | 对应数据链进入“未配置”，不自动回退到旧库 | 重新导入、在线更新或显式选择可用历史版本 |

交互规则：

- 规则管理必须显示来源、武器、用途、完整 Perk 组合、当前数据 revision 和受影响的账号实例数，不能只显示难以辨认的内部 ID。
- 点击“移除规则”默认写入可恢复的本地排除记录。发布方原始规则保持只读，后续更新不会把玩家已经移除的同一规则静默恢复。
- 玩家自建的个人推荐仍使用现有独立管理能力，允许编辑、停用和永久删除，不与发布方来源混在同一列表。
- 来源状态固定为 `active / disabled / removed`：`disabled` 保留本地规则并排除匹配，可立即恢复；`removed` 删除该来源的本地规则并保留来源 tombstone，重新导入或更新后也不得静默启用，必须由玩家显式恢复。
- 停用或移除来源前显示规则数、覆盖武器数和当前账号受影响实例数；确认后只重算受影响来源覆盖的武器。
- 删除整份数据集属于破坏性操作，必须二次确认，并明确删除对象、当前 revision、恢复方式以及不会删除的账号标签、备注、锁定和配装。
- 删除当前激活数据后显示“未配置”，不得自动启用旧的 `unverified` 数据，也不得用残留匹配缓存继续给出结论。
- 导入新版数据时保留玩家的来源停用和规则排除设置。无法继续确认同一条规则身份时，将排除项标记为“需要复核”，不能静默套用或丢弃。
- 重新导入包含已移除来源的数据时，预览必须显示“该来源仍处于已移除状态”；只有玩家选择恢复后才重新参与匹配。
- 批量整理预览存在时禁止修改来源或规则；若推荐 revision 已变化，旧预览立即失效，玩家必须重新预览并确认。
- 批量标签使用一次本地批量提交；“清理”提交前仍按结构化保护索引排除强保护实例，不逐件重复写入。

发布方数据和玩家纠错记录分层保存，避免更新、恢复和审计互相覆盖：

```text
recommendation_source_overrides
  source_id
  enabled
  updated_at

recommendation_rule_overrides
  source_id
  rule_stable_id
  enabled
  reason
  source_revision
  updated_at
```

`rule_stable_id` 必须来自来源、武器官方身份、用途和精确规则组合等稳定语义，不得依赖 SQLite 行号或界面顺序。原因可选，仅供玩家自己识别为何移除。

## 4. 缓存、刷新与性能

### 4.1 数据分层

| 数据层 | 内容 | 规则 |
|---|---|---|
| 稳定定义缓存 | Manifest、图标、装备定义、插槽定义、完整可掉落池 | 按 Manifest 版本持久缓存 |
| 推荐知识缓存 | 四人工来源、DIM Wishlist | 按数据 revision、commit、ETag 或指纹保存 |
| 派生计算缓存 | 实例推荐摘要、核心状态、六项证据 | 按 Roll 指纹和所有依赖版本保存 |
| 上次成功账号快照 | 仓库、角色背包、已装备、邮政官和实例 Roll | 只作启动占位、离线查看和失败回退 |
| 当前账号 Store | 最近接受的 Profile 与 Bungie 成功写操作返回的局部 patch | 不使用 TTL；相同/旧 Profile 不回退页面，新 Profile 自然校准 |
| 当前写操作状态 | 当前按钮的提交中、成功或失败 | 不持久化，不进入全局同步状态或后台任务 Dock |

上次账号快照无论多新，应用重启后都必须标记为“上次同步数据”。仓库不建立独立缓存，它是当前账号 Store 的派生视图。

`dim-api` 只作为数据边界参考，不引入依赖、不复制代码，也不调用 DIM Sync。它证明 DIM 自己也只持久化标签、备注、配装和设置等应用数据，不保存 Bungie 实时库存。组件增量和离线更新队列只用于应用自有数据，不能套到 Bungie Profile。

匹配缓存键至少包含：

```text
accountKey + instanceId + itemHash + rollFingerprint
+ manifestVersion + knowledgeRevision + dimRevision
+ recommendationOverrideRevision + matchingAlgorithmVersion
```

位置、光等、锁定、装备状态和玩家标签不进入 Roll 指纹。

### 4.2 统一账号同步

账号、仓库和设置页的同步入口调用同一个权威动作：

```text
Bungie Profile
  → 紧凑账号快照
  → 实例差异
  → profile_minted_at 水位线检查
  → 原子提交当前账号 Store
```

实例差异只区分新增、删除、位置、锁定、装备和 Roll 变化。仓库同步关键路径不得包含标签读取、CSV 校验、推荐库重建、全账号推荐重算、完整可掉落池或同名实例详情。

刷新所有权固定为：

- 主进程启动只恢复资料库运行时、上次账号快照和稳定本地资源，不远程刷新账号。
- 全局账号控制器每次运行只执行一次可见初始同步。
- 页面挂载、切换菜单和打开详情不触发账号同步。
- 推荐核对只在账号快照已经提交后作为非阻塞派生任务启动；菜单挂载不拥有推荐刷新动作，位置等非 Roll 变化通过匹配缓存直接复用。
- 攻略匹配、助手匹配等只读消费者只读取当前全局账号快照；配装执行前后的复核必须调用全局账号控制器，不得在功能内部保留直接强刷 Profile 的 fallback。
- 手动同步穿透账号缓存；普通请求不能阻挡或替代权威请求。
- 同步失败保留当前 Store；本次运行尚未成功同步时继续显示明确标记的历史快照。
- 首页情报、账号战绩、商人和资料库分别维护自己的刷新范围与时间。

禁止账号固定轮询、TTL、stale-while-revalidate，以及只更新 Session、Repository 或磁盘但不提交 Renderer Store 的后台刷新。

账号写后一致性继续由 [Bug #22](Bug-22-account-refresh-write-consistency.md) 跟踪。

### 4.3 写操作完成与后续校准

普通转移、锁定、装备、邮政官取回和配装写入统一使用：

```text
提交中 → Bungie 已受理 → 本地局部状态已应用
     ↘ 提交失败
```

- Bungie 明确返回成功后立即把返回的 `account_patch` 提交到共享账号 Store 的确认态，不登记 Pending，也不等待 Profile 才显示结果。
- 普通写操作不调用 `startAccountWriteVerification`，不创建 `account-write-sync`，不执行 `750ms / 2s / 5s / 10s / 20s` 轮询，也不在终态或超时后强制完整账号刷新。
- 接口成功但缺少 `account_patch` 时只显示短提示；下次 10 分钟定时同步、回到前台补同步或玩家手动同步负责校准，不立即传输完整账号快照。
- 相同或旧 Profile 仍不得重建当前页面；后续真正前进的新 Profile 作为服务器事实自然覆盖本地局部结果。
- 配装中的“转移后立即装备”属于步骤依赖，不使用通用后台确认任务；主进程只针对相关实例读取目标角色 inventory / equipment，确认进入背包后才提交装备接口。
- 普通写操作不进入顶部账号状态或后台任务 Dock。当前按钮只显示提交过程，完成后显示一次短结果；静默账号推送不制造重复绿色横幅。
- 标签、备注和玩家整理状态属于本地写入，持久化成功后可直接更新本地 Store，不进入 Bungie 后台确认。

#### 4.3.1 当前问题证据与根因

真实账号记录已确认当前实现存在以下闭环缺口：

- 本地写操作日志有 8 条 `partial/unconfirmed`；之后的账号快照中 1 件已出现在目标角色，另外 7 件在仓库、角色背包、已装备和邮政官中均无法定位。已反映的 1 件能够清除，缺失的 7 件继续留在 `committedPatchesByInstanceId`；新提交 1 件后顶部由 7 增为 8。
- `unconfirmed` 终态只触发一次权威刷新，Renderer 只丢弃明确 `mismatch` 的补丁；实例缺失产生的空 mismatch 集合不会清除 Pending。后续账号快照又通过旧实体恢复和补丁重放继续保留预计位置，形成永久 Pending 与幽灵投影。
- 顶部数量取 Store Pending 与当前任务跟踪数量的最大值；只要有一个新任务运行，全部历史残留都会被显示为仍在确认。账号同步横幅则把快照到达时的数量写入字符串，之后不会随 Store 更新，因此会出现顶部 8、横幅 7、当前操作 1 的冲突。
- 当前每个操作独立执行最多 5 次确认读取，等待序列为 `750ms / 2s / 5s / 10s / 20s`。现有调试记录包含 78 个操作、334 次确认读取，平均约 `990ms`、P95 约 `3.06s`、最慢约 `6.57s`，其中 53 次到达第 5 次读取。
- Account Session 会把本次三组件确认与缓存中的完整组件集合做并集，使所谓轻量确认退化为接近完整 Profile 的强制刷新。
- 每次后台任务状态变化都会由主进程发送完整任务数组；Renderer 无条件替换并通知全部订阅者。完整任务列表同时进入设置根 Hook、写操作根 Hook 和 Product Shell，重新创建菜单 Context，使仓库筛选、推荐派生和虚拟网格测量被反复触发。
- 现有滚动性能脚本只覆盖手动账号同步，没有覆盖连续取出、加锁、多项 `account-write-sync` 和终态交错，因此原有同步期间 60 FPS 结果不能作为 Bug #33 的验收结论。

本轮采用 DIM 的完成边界直接切断上述链路：普通写入成功后只更新受影响实体，因此不再产生逐操作轮询、任务进度广播、历史 Pending 累加和异常终态的 8MB 完整快照重建。此前的三组件缓存修复与后台任务窄订阅继续作为正常同步和其他长任务的性能保护。

#### 4.3.2 单一状态所有权与玩家反馈

普通写操作状态以当前 API 调用为唯一事实，各区域只消费自己需要的粒度：

| 区域 | 允许展示 | 禁止展示 |
|---|---|---|
| 当前按钮 | `取出中…`、`加锁中…` | 全账号 Pending 数量 |
| 短时操作提示 | `已取出到术士`、`已加锁` | `正在后台确认`、重复成功详情 |
| 受影响卡片/详情 | 当前提交状态、一次成功或失败结果 | 页面级任务说明、持续同步状态 |
| 顶部账号状态 | 手动、初始或低频账号同步状态 | 普通写操作数量、`n 项待确认` |
| 仓库账号横幅 | 手动同步发现的外部变化、同步失败 | 当前写操作 Pending 数量和应用刚执行过的同一变化 |
| 后台任务 Dock | 应用/资料库等真正长任务 | 每个普通写操作的确认任务 |
| 设置操作日志 | 完整写操作结果与错误历史 | 驱动仓库页面实时渲染 |

“待定”只表示玩家的整理决定。普通写操作不再产生“同步中 / 游戏状态延迟 / 明确冲突 / 无法定位”状态；后续正常账号同步只在手动发现外部变化时展示汇总，避免同时显示“已取出”和“1 件装备移出仓库”。

#### 4.3.3 后台任务与渲染隔离

- 后台任务 IPC 使用 `{ taskId, changedFields }` 增量事件更新 Renderer 的 `Map<taskId, task>`；内容无变化时不增加 revision、不通知订阅者。
- 完整任务列表只由设置页在挂载时订阅；Product Shell 只订阅更新 Dock 所需的应用/资料库任务小切片，普通账号写操作不订阅后台任务。
- `useDiagnosticsSettings` 不再把完整 `backgroundTasks[]` 带入根级 `useDesktopProductShell`；后台 Dock 使用独立订阅组件或稳定 Store 接口，不通过 `DesktopMenuSession` 广播。
- `DesktopMenuSession` 拆分为导航、账号数据、账号动作、仓库数据、写状态和诊断等窄 Context。仓库不得因应用更新进度、资料库任务、商人刷新或设置页日志变化而重渲染。
- 账号 Store 继续向直接读取规范化状态的实体级 selector 演进。仓库最终应订阅稳定 item key 列表，每张卡订阅自身实体；单件锁定只更新该卡，单件取出只更新位置索引、目标角色索引和对应实体。
- 虚拟网格只在容器宽度、密度、列数或稳定卡片高度变化时测量；锁定、同步、推荐和任务状态变化不得因 `items` 数组引用变化触发 `getComputedStyle / getBoundingClientRect`。

### 4.4 推荐增量更新

| 账号变化 | 页面处理 | 推荐处理 |
|---|---|---|
| 位置、锁定、装备变化 | 更新实例事实 | 复用匹配结果 |
| 新增实例 | 添加卡片 | 只计算新实例 |
| 删除实例 | 删除卡片 | 删除对应摘要 |
| Roll 指纹变化 | 更新实例 Roll | 只重算该实例 |
| Manifest 或推荐 revision 变化 | 保留账号事实 | 按依赖版本失效 |
| 来源停用或规则移除 | 保留账号事实 | 只重算该来源覆盖的受影响武器 |

运行时只读取已经激活的推荐 SQLite。CSV 预览、语义校验和知识库重建只在导入或更新阶段执行。账号同步后不得无条件重新扫描全部武器。

### 4.5 详情渐进加载

详情首屏由四类本地数据组合，不等待一个“完整详情对象”：

```text
当前账号 Store：位置、锁定、光等、当前实例 Roll
Manifest 缓存：名称、图标、框架、属性和说明
推荐缓存：核心结论与来源摘要
本地数据：标签、备注和配装保护
```

- 点击后立即显示首屏，不出现详情全局 Loading。
- 完整可掉落池默认折叠，玩家展开后才按 `itemHash + manifestVersion` 从本地 Manifest 读取并持久复用。
- 实例完整 Roll 默认折叠，玩家展开后才按 `instanceId + rollFingerprint` 读取；相同实例未发生 Roll 变化时跨详情和同名整理复用。
- 打开详情、进入同名组或切换同名实例不得自动读取实例完整 Roll。玩家在同名组选择“完整 Roll”后，才使用有并发上限的队列逐件补齐，并允许单件重试。
- 当前启用 Perk 来自账号紧凑快照，应立即显示，不得等待实例完整 Roll。
- 实例插槽配置只在摘要不足、玩家主动展开、主动重新读取或写后确认需要复核时访问 Bungie。
- 打开详情不得触发全账号刷新。
- 同名整理直接使用紧凑 `weapon_roll`，切换同名组不得并发读取组内所有实例详情。
- 相同 Roll、Manifest 和推荐 revision 下，重复打开同一武器不重新读取或计算。
- 延迟数据只更新自己的固定区域，不能让弹窗主体结构在数秒后跳变。

### 4.6 显式工作流与渐进披露

仓库使用三个始终可见、可直接跳转的任务入口：`1 浏览装备`、`2 看推荐`、`3 整理同名`。它们是玩家路径，不是必须依次完成的向导。

“看推荐”首屏只保留：

- 一个当前任务说明，例如“先选择来源，再按 Perk 与完整命中数定位装备”。
- 先选择 Aegis、LGpig、YXCRALLXY、Sayalarry 或 DIM。人工来源第二步按真实核心 Perk 要求显示 `x/y / 未要求 / 无法判断 / 未收录 / 全部`，第三步再用下拉选择完整要求的精确 `x/y`；DIM 没有固定核心栏位，第二步直接显示最佳组合的精确 `x/y / 未指定组合 / 无法判断 / 未收录 / 全部`，不再显示第三步。用途、位置和玩家标记等收入“更多筛选”。
- 武器身份、真实位置、核心状态、最多一条主要来源摘要和“查看依据 / 整理同名”操作。
- 一个“推荐来源”入口，负责数据更新、来源停用、按来源删除和单条规则移除。

以下内容不得常驻推荐结果首屏：

- 四格核对统计、来源状态长列表和重复的结果解释条。
- DIM 规则总数、短 commit、CSV 来源记录数和逐阶段扫描文案。
- “复制验收报告”等维护者操作。
- 本地文件、粘贴文本、标准模板等低频导入方式。

正常状态应保持安静：账号同步与推荐核对完成后只保留短状态和时间。异常、部分可用或数据未配置时，在固定状态区显示原因和唯一主操作，不让异步完成造成页面整体跳动。

详细信息按层级进入：

| 层级 | 内容 |
|---|---|
| 结果行 | 玩家此刻需要做的判断和下一步操作 |
| “查看依据”详情 | 六项证据、全部来源、用途、规则说明和保护原因 |
| “推荐来源”覆盖层 | 来源启停、按来源删除、单条规则移除、更新与恢复 |
| “其他导入方式” | 本地文件、粘贴文本、模板导出和高级维护 |
| 设置诊断 | 核对数量、规则总数、revision、commit 和验收报告 |

覆盖层打开后限制焦点，关闭后返回触发按钮；三个任务入口和结果列表使用 roving focus。窄屏保持同一信息顺序，结果行改为纵向布局，来源管理使用全高覆盖层，不维护另一套页面。

### 4.7 浏览装备的推荐筛选与单件快捷操作

武器浏览模式在结果列顶部按“先来源、再核心 Perk、后完整命中”筛选。来源只列当前已配置且启用的 Aegis、LGpig、YXCRALLXY、Sayalarry 和 DIM；即使某个来源在当前账号或当前筛选范围内覆盖为 0，也必须保留在来源选择中，不能因没有命中实例而消失。未选择来源时显示全部当前范围装备，不提供容易混淆的多来源综合结果筛选。

人工来源选择后，第二步显示该来源真实核心 Perk 要求的精确命中数，例如 `2/2、1/2、0/2`；只要求一个核心栏时显示 `1/1、0/1`，没有核心要求显示“未要求”，核心栏数据不完整显示“无法判断”，来源没有该武器规则显示“未收录”。第三步使用单选下拉显示完整明确要求的精确命中数，例如 `6/6、5/6、4/6`，分母按每条来源规则的真实要求计算，不能固定写死为六。DIM 没有固定 Perk 1 / Perk 2 栏位，第二步改为“最佳组合”，直接显示精确 `x/y`；未指定组合、无法判断和未收录必须保持独立，不显示人工来源的第三步。

工作流栏只保留“浏览装备 / 看推荐 / 整理同名”和必要的账号、推荐异常状态；正常完成态不再同时重复账号武器总数与当前结果数。结果列只保留一条命令栏，按键盘顺序承载来源、核心 Perk 或 DIM 最佳组合、其他特殊状态、完整命中、结果摘要和批量入口。搜索、来源、其他状态和完整命中由控件自身文字表达，不再在控件上方重复微型标题；核心命中不能只显示相邻数字，选项固定写成“命中 x/y”或“未命中 x/y”，数量使用独立徽标，悬停和可访问名称说明“命中数 / 要求数”。完整筛选当前值固定带“完整”前缀。未要求、无法判断和未收录收入“其他状态”下拉；中窄屏允许同一命令栏内部紧凑换行，但不得重新拆成多条常驻工具栏。

左侧筛选按语义分层：物品范围使用最明确的连续分段选中态；槽位、装备阶级和整理状态使用中性连续分段结构；查看范围使用带单选标记、右对齐数量和行分隔的连续列表；稀有度、弹药与伤害属性保留游戏事实色，但未选中时降低饱和度、选中时同时增强底色和内描边。文本输入使用内凹底色、弱边框和搜索图标；下拉框使用更明确的边框、独立箭头区和右侧分隔线；操作按钮使用较高字重和动词图标，不能再与字段共用同一种无提示矩形。全部筛选的重置入口与搜索输入同一行，因为它同时影响左侧条件和结果列推荐条件；入口始终占位并显示重置图标与独立条件计数，宽屏在左侧独立滚动时保持可见，无条件时仍需保持可识别的禁用态，窄屏恢复普通文档流以免叠加顶部导航。

按钮颜色不按动作名称任意分配：共享 Primary 默认使用操作蓝；手动刷新、同步当前数据和失败后的重新读取使用带刷新图标的独立绿色 Refresh Control；绿色仍可表达成功、可用和明确符合，红色只用于真实危险或失败，紫色只用于 AI。仓库卡片中的“加锁 / 解锁”使用无底或弱边框 Quiet，“取出”使用中性 Secondary；重复卡片不得铺满实色主按钮。玩家选择“清理”只是写入可逆本地整理状态，不使用危险按钮表面；最终转移仍明确说明不会自动分解。普通状态不显示条件标签行、批量教学占位或“没有附加条件”空行，进入批量选择后才展开选择与写操作区。没有已标记清理装备时隐藏清理转移说明。

数量随搜索、位置、槽位、类型、稀有度、锁定和整理状态等其他条件变化。核心 Perk 各选项数量忽略当前核心与完整命中筛选；完整命中选项只基于当前核心 Perk 条件计算。推荐核对未完成时，没有现成实例结果的武器不得计入“未收录”。数量为 0 的按钮保留位置但禁用。所选来源在卡片和结果行中固定优先展示，切换到护甲或装备时重置来源、核心 Perk 与完整命中筛选。

“浏览装备”和“看推荐”必须共用同一个来源、核心 Perk、完整命中状态和实例筛选事实索引，切换工作区时不重置玩家刚选的条件。同一来源存在多条规则时，按卡片摘要相同的优先级只选最佳一条作为该实例的筛选事实；不能把多条规则累计成一个虚假的命中数。同一来源的多条规则只算一个来源，卡片来源数和结果行“另有 n 个来源”不得按规则条数重复计数。内部 `full / core / close / key_missing / not_matched / weapon_only / uncheckable` 状态继续用于排序、保护和冲突判断，但不再作为普通玩家的筛选分类或结果主文案。

左侧带数量的筛选项采用分面口径：每个选项应用除自身维度外的其他已生效条件，选中项数量应与切换该维度后可得到的结果一致。物品范围明确显示账号总数；武器槽位、查看范围、武器类型和框架显示当前其他条件下的可用数量，不能一部分使用全账号固定总数、另一部分使用当前结果数。

推荐数据或 revision 变化时，先为账号武器建立一次实例轻量筛选事实索引，每条事实只保留来源、核心 Perk 键、完整命中键、DIM 最佳组合键和可核对状态。筛选按钮、装备列表、“看推荐”和各分面数量共同复用该索引；点击筛选时只比较字符串与数字，不得重新遍历来源规则、完整 Roll 或 Wishlist，不触发 Bungie、SQLite、账号同步、推荐核对或图标读取。只切换来源且后续条件仍为“全部”时，槽位、位置、武器类型和框架的候选范围没有变化，不应重新扫描这些分面。

仓库筛选上下文会进入全局 AI 页面上下文，但只有内容真正变化时才能更新全局状态。来源管理读取返回与当前相同的来源快照时必须保持原引用，Desktop 接线中的推荐刷新回调也必须稳定；不得形成“筛选变化 → 写全局上下文 → Shell 重渲染 → 来源重新读取 → 再写全局上下文”的反馈循环。

### 4.8 资料库定义详情保留来源原始形态

资料库定义详情只展示公开推荐资料，不存在玩家持有实例，也不执行 Roll 命中核对。推荐数据进入资料库 UI 前必须保留来源原始表达，禁止为了复用实例匹配界面而统一展开或合并：

- 数据源明确给出完整组合时，保留每套组合的边界并按组合展示；多套组合互为可选，不跨组合累计或重组 Perk。
- 数据源给出分栏候选池时，每条来源规则只显示一张 Perk 池卡；同栏多个候选标明“任选其一”，不同栏保持独立，不计算笛卡尔积，不生成推导组合。
- 四个人工来源 CSV 的栏位字段属于来源规则和候选池；`source_records.requirements` 是资料库展示与实例匹配的共同事实。只有 DIM 原生 Wishlist、遗留自定义完整规则等明确组合来源进入 `combos`。
- 普通版、强化版、历史版等同名 Perk Hash 只用于定义解析与实例核对；资料库按玩家可见 Perk 身份展示，不能因为 Hash 不同重复生成视觉相同的组合。
- `source_records.requirements[].candidates` 中已解析的 Hash、同名 Hash 集合、图标、官方说明和英文名必须完整进入详情 ViewModel；UI 优先使用这些来源候选信息，当前查看版本的 Perk 池只作视觉兜底。大师属性别名和仅存在于关联版本的推荐项不能退化为无图标、无说明占位。
- 资料库推荐区不显示“命中 / 未命中”“Perk x/y”“完整 x/y”“未选择账号装备”或命中颜色。实例详情继续独立消费 `source_matches` 显示核对结果。
- 推荐数量统计真实显示的来源规则或真实完整组合，不统计任何推导结果。Aegis、LGpig、YXCRALLXY、Sayalarry 与 DIM 继续保持独立来源，DIM 固定排在人工来源之后。

浏览装备卡片在非整理模式提供两个单件快捷操作位：

- `加锁 / 解锁`：仅对有实例 ID 的装备显示；未锁定时显示“加锁”，已锁定时原位切换为“解锁”，只提交当前状态对应的目标操作。
- `取出`：仅对仓库中的实例显示，目标固定为当前角色；角色背包、已装备、邮政官和其他角色装备不伪装成可直接取出。

这些操作都不弹二次确认，因为它们是可逆的显式单件动作。一次只允许执行一个快捷写操作；当前按钮显示进行中，其他快捷按钮暂时禁用。失败后保留卡片并显示 Bungie 返回的真实原因；加锁或解锁成功后焦点回到同一卡片主入口，当前锁定筛选使卡片离开结果时焦点移动到下一件，末项则回到上一件；取出成功且卡片离开当前仓库结果时使用相同焦点规则。快捷按钮必须作为卡片主按钮的兄弟节点，保持 Tab 可达，不能形成嵌套按钮；武器虚拟网格的固定高度、测量步长和焦点恢复必须同步更新。

结果区不再维护“浏览 / 选择候选”伪 Tab、重复物品范围下拉或按标签自动选候选的第二套筛选。默认只显示“批量选择”；进入后先显示“已选 n 件 / 选择当前结果 / 清空选择”，再显示独立操作区。玩家整理操作只提供“保留 / 待定 / 清理”，同时保留真实的批量加锁和移动仓库所选；接收角色属于移动操作参数，不得混入筛选。批量加锁跳过已锁定或无实例 ID 的装备，并逐项返回成功与失败摘要。

## 6. 验收条件

### 数据与匹配

- 四人工来源与 DIM 原生 Wishlist 完全拆分。
- 四人工来源在当前 Manifest 下严格校验为 0 阻塞。
- “操控 → 操控性”“伤害 → 冲击”等宽松关系被阻止。
- 旧人工来源 SQLite 未验证时不参与任何结论。
- DIM 原始组合、说明、标签和不可确认 Hash 不丢失。
- 资料库定义详情忠实保留来源形态：完整组合仍为组合，分栏候选仍为 Perk 池；禁止从候选池推导组合。
- “完美逆行”等跨版本多候选武器的攻略推荐数量按真实来源规则闭合，不再因普通版、强化版或历史版 Hash 笛卡尔积出现几十或上百张重复卡。
- “完美逆行”的填装速度、高速发射、切割等大师别名或跨版本候选直接使用来源解析后的官方图标和说明，不依赖当前查看版本池再次猜测。
- 每个实例使用自身 Roll，核心状态只看来源要求的 Perk 1/2。
- 同为 `5/6` 时，缺低优先级项与缺核心 Perk 显示不同结论。
- 暗夜魅影光等 413 的 Aegis 结果应为 `Perk 0/2 · 完整 2/6`；大师“填装速度”与本件“大师杰作：稳定性”明确显示“不符”，不能出现“数据未读取”或“待核对”。
- 暗夜魅影光等 324 的大师与起源特性均应显示“不符”，不能因为推荐 Hash 未解析而进入未知状态。
- 老版本武器完整 Roll 没有起源栏时显示“不符”，详情中的本件值显示“本版本无此栏位”。
- 单条规则移除后只影响对应来源与武器，且可以恢复。
- 整个来源停用后不参与匹配、排序、推荐保护或批量整理，其他来源不受影响。
- 删除当前人工推荐数据或 DIM Wishlist 后进入“未配置”，不会回退到旧的未验证数据。
- 导入新 revision 不会静默丢失或错误套用玩家的来源停用与规则排除设置。

### 缓存、刷新与性能

- 本次运行只有一次可见初始账号同步，没有主进程与 Renderer 双刷新。
- 账号、仓库和设置页共用唯一权威同步，仓库不存在独立远程缓存。
- 游戏内移动装备后，同步一次即可同时更新账号、仓库和配装。
- 晚到的相同或旧 Profile 不会恢复旧位置；后续前进的新 Profile 自然校准本地局部结果。
- 写接口成功后立即更新共享页面确认态，不创建逐实例 Pending 或持续同步提示。
- 连续提交 5 个普通单件操作不会创建 `account-write-sync`、五轮 Profile 请求或 75 秒终态完整刷新。
- 顶部账号状态、仓库同步横幅和任务 Dock 不展示普通写操作的确认进度；每次操作只出现一次短结果。
- 完整账号快照只在初始、手动、低频自动同步或配装明确要求的前后复核中构建和传输。
- 仓库同步不等待推荐重算、CSV 校验、完整池或同名实例详情。
- 位置、锁定、装备和标签变化不重新计算相同 Roll。
- 同一武器重复打开不重新读取已有定义、当前 Roll、推荐摘要或完整池。
- 完整池只在玩家展开后加载；同名组不自动读取全部实例详情。
- 人工推荐 CSV 自动校验按文件状态与 Manifest 版本记忆结果；同一份阻塞数据不会在每次打开详情或重新核对仓库时重复执行完整校验。
- 详情推荐摘要按账号/Manifest 作用域、推荐 revision 与武器身份复用，并对并发请求去重；来源或规则变化后使用新 revision 自动失效。
- 同名整理的完整 Roll 结果、读取状态和并发请求统一按实例当前 Roll 指纹保存；账号同步导致 Roll 改变后不会继续复用旧对比数据。
- 详情缓存作用域只使用账号身份、Manifest 版本和语言；同版本资料库仅更新时间变化不会清空定义、Roll 或推荐摘要缓存。
- 持久化实例详情 SQLite 按账号、Manifest 版本和实例 ID 隔离；资料库升级后账号 Session 与完整 Roll 缓存同时切换版本，不会复用旧定义构建的详情。
- 仓库页面自身不发起账号轮询或切页刷新；应用级低频自动同步提交共享 Store，失败时继续显示旧数据，不静默清空或替换列表。
- 推荐删除只触发对应推荐 revision 的事件更新，不触发 Bungie Profile 或全账号同步。
- 200 件以内的武器结果保持稳定挂载，由 `content-visibility` 跳过屏幕外布局与绘制；更长列表只保留可见窗口。滚动热路径只允许读取 `scrollTop` 并按已缓存尺寸更新窗口，不得同步测量网格或通过观察网格自身高度触发 `ResizeObserver` 反馈链。
- 已在本次会话加载的游戏图标直接复用浏览器与内存缓存，不重复读取 CacheStorage；持久缓存写入成功后，本次会话不再重复执行存在性检查。
- 普通账号写操作只产生单件 Store patch，不得使 `HomePage`、无关菜单 Context 或整个仓库列表因后台任务进度反复重渲染；设置页关闭时不订阅完整后台任务历史。
- 约 1000 件武器场景连续执行 5 次取出/加锁并同时滚动时，单件 Store patch 不触发全仓推荐重算或虚拟网格同步布局测量，操作完成后不存在账号写任务继续占用界面。
- 推荐匹配刷新只比较账号中的武器实例与 Roll 指纹；取出、存入、装备、锁定等位置或状态变化不得清空推荐结果或重新核对全部账号武器。

### 安全与 UI

- 卡片、推荐结果、同名整理和详情使用相同核心状态。
- 详情中的人工来源以“图标 + 名称 + 短状态”表达同栏候选“任选其一”；名称必须常驻可读，同名多 Hash 合并成一个玩家候选。只有本件实际命中的候选使用绿色边条和勾，当前启用同时使用独立蓝点与“当前”文字，未命中的合法备选不显示红叉或整体灰隐。
- 武器属性只显示当前对象对应的数值，宽屏使用三列紧凑矩阵，小屏使用两列；不显示属性条，也不逐项重复标准值、读取状态或比较说明，待应用变化只显示数值箭头。
- 武器详情不再显示或加载个人知识表单，已有旧记录不参与详情推荐与 AI 分析上下文。
- 推荐 Perk 图标可通过鼠标悬浮、键盘聚焦和触屏点击查看官方名称、说明、来源身份与本件状态；关闭支持 `Escape` 和点击外部，缺少图标时保留可读文字回退。
- DIM 继续按独立完整组合显示，组合内逐项使用相同的图标、常驻名称与命中状态，不把多套组合合并成候选池，也不使用与命中语义重复的拇指标记。
- 资料库定义详情的推荐区只展示来源、用途、说明和原始 Perk 池或完整组合，不显示命中状态、匹配分数、完整度或“未选择账号装备”。
- 首层直接显示“浏览装备 → 看推荐 → 整理同名”，无需理解数据源或核对流程才能开始使用。
- 推荐结果首屏不常驻核对矩阵、来源长列表、规则总数、revision 或验收报告。
- 选择具体来源后，可用核心 Perk、完整要求或 DIM 最佳组合的精确 `x/y` 直接到达对应实例；未要求、无法判断与未收录保持独立，详细来源和六项证据按需展开。
- 浏览装备顶部与推荐结果列表使用相同的“来源 → 核心 Perk x/y → 完整 x/y”状态；DIM 使用“来源 → 最佳组合 x/y”。数量跟随其他条件变化，核对未完成的未知实例不进入“未收录”。
- 同一来源存在多条规则时按卡片相同优先级选择最佳一条作为筛选事实，不跨规则累计命中；来源数量不按规则条数重复累计。
- 数量为 0 的命中选项不可点击；“浏览装备”和“看推荐”切换后保留同一来源、核心 Perk 与完整命中条件。
- 浏览装备的整理状态只显示“保留 / 待定 / 清理”，没有选中项表示全部，再次点击当前项取消筛选；未设置只作为内部状态保留，不改写现有玩家标签。
- 武器查看范围不再显示“随身待检查”和“全账号武器”，只保留仓库整理、当前背包、当前已装备、当前邮政官和其他角色；跨页定位仍可临时使用内部全账号范围。
- 删除左侧“保护与匹配”筛选；DIM 由推荐来源承接，配装引用继续作为自动保护与卡片事实，个人目标由“看推荐 → 我的目标”承接。
- 仓库筛选上下文改为非渲染快照，选择来源或结果不得更新全局 Shell React state；推荐来源管理只在进入页面或 revision 明确变化时读取。
- 宽屏仓库固定共享页头和顶部工作流区，左侧筛选与右侧结果独立滚动并阻止滚动链；工作区切换保留各自结果位置，`850px` 及以下恢复单一页面滚动。
- 正常状态只显示短状态和时间；异常状态提供原因与唯一主操作，异步更新不改变主体布局。
- 写后正常状态只在按钮和受影响卡片/详情中短时展示；顶部、页面横幅和任务 Dock 不描述普通写操作的后台确认，因为该确认链路不再存在。“待定”只用于玩家整理状态。
- 单件和批量锁定显示保护项、成功项与失败项。
- 批量选择只基于当前正式筛选结果，不再提供“选择候选”下拉；筛选、选择和写操作位于独立区域。
- 非整理模式的实例卡可一键加锁；只有仓库实例可一键取出到当前角色，失败时保留卡片并显示真实原因。
- 单件加锁后焦点回到原卡片；取出导致卡片离开结果时焦点进入相邻卡片，快捷按钮可通过 Tab 到达且不与卡片主按钮嵌套。
- 推荐结论不自动修改玩家标签或游戏锁定状态。
- 强制保护项不会进入自动操作。
- 移除规则、停用来源和删除数据集前显示具体影响范围；删除数据集必须二次确认。
- 推荐数据操作不清除玩家标签、备注、游戏锁定或配装引用。
- 批量整理预览期间不能修改推荐规则；revision 变化后旧预览不得继续执行。
- 最终分解只能由玩家在游戏内完成。
- 护甲页面、护甲筛选和 Armor Planner 不受影响。

## 7. 不在范围

- 自动或远程分解 Destiny 2 装备。
- 自动创建配装或覆盖玩家标签。
- 接入或调用 DIM Sync API。
- 把未获授权的第三方资料打包进公开安装包。
- 批量抓取或镜像 light.gg。
- 使用 AI 猜测武器、Perk、版本或作者未表达的组合。
- 护甲清理和 Armor Planner 规则改造。

## 8. 完成条件

代码开发状态与数据内容状态分开：S0–S18、S21–S23 当前范围已完成，S19–S20 已完成高收益第一阶段但仍需真实账号验证是否继续实体级结构升级；全部切片完成、真实账号与实窗验收通过，并且四人工来源外部数据严格校验达到 0 阻塞后，T20 才能标记为全部完成。

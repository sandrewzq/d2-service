# T20：武器推荐与仓库整理

> 更新时间：2026-09-06
> 状态：🟡 S0–S13 代码开发完成，待整体验收；外部推荐数据已通过当前 Manifest 严格生成
> 优先级：P1

## 1. 目标与边界

仓库页帮助玩家完成四件事：

1. 判断一把武器是否符合某个推荐来源。
2. 在同名武器之间优先比较 Perk 1 与 Perk 2。
3. 保护锁定、配装引用、玩家手动保留和无法安全判断的实例。
4. 由玩家确认锁定、标记或转移，最终分解仍在游戏内完成。

仓库首层必须直接展示玩家工作流，而不是先展示核对统计和数据源细节：

```text
1 浏览装备
  → 2 看推荐：符合推荐 / 部分符合 / 未符合 / 无法判断 / 无推荐
  → 3 整理同名：重点比较 Perk 1 与 Perk 2
  → 玩家显式标记、锁定或转移
  → 游戏内完成最终分解
```

账号同步是这条流程的前置状态，不是额外工作区。正常时只显示“已同步时间”；未同步、同步中或失败时才显示可执行提示。

应用不得自动生成“应该分解”的结论，不得自动锁定、解锁、保留、转移或分解。

## 3. 推荐数据与匹配

### 3.1 两条数据链

应用展示五个来源，但底层必须分开：

```text
Aegis / LGpig / YXCRALLXY / Sayalarry
  → 31 列严格 CSV
  → Manifest 语义校验
  → 人工来源 SQLite

DIM 社区愿望单
  → 原生 itemHash + perkHash 组合
  → 原生解析与诊断
  → DIM SQLite

两条数据链
  → 按 instanceId 核对玩家实际 Roll
```

DIM Wishlist 来自 GitHub 或玩家本地导入，与 `dim-api` 的 DIM Sync 服务无关。

### 3.2 导入格式与严格语义

普通玩家使用简表导入，不要求填写采集证据或 Manifest 展示字段：

```text
武器 / 武器ID（可选） / 英文名称（可选） / 推荐来源 / 用途
第一列 / 第二列 / Perk 1 / Perk 2 / 大师 / 起源特性 / 评级 / 备注
```

应用根据武器名称或 ID 读取当前 Manifest，自动确认官方武器身份并补齐武器 ID、分类、图标和来源信息；英文名称可以留空，不参与中文简表的必要校验。当前 31 列格式保留为 T20 完整数据包和旧版本兼容格式，不作为普通玩家模板；DIM Wishlist 继续使用独立文件和独立数据链。

来源管理中同时提供“导出玩家模板”和“导出当前推荐”：前者生成空白简表，后者把当前人工来源转换为简表，便于玩家修改后再导入；完整 31 列证据数据不进入普通导出。玩家简表固定执行合并更新，只新增或更新对应来源与武器规则，不删除文件中未出现的已有推荐；只有无异常的 31 列维护者完整包执行整体替换。任一格式存在异常行时只忽略对应行，其余有效行合并导入，已有正确规则继续保留。

### 3.3 严格语义

人工来源的武器、第一列、第二列、大师、Perk 1、Perk 2 和起源特性只接受：

1. 官方 Hash 精确命中；或
2. 规范化后的 Bungie 官方全名完全相同。

人工来源简表或完整 CSV 的来源身份只接受 Aegis、LGpig、YXCRALLXY 和 Sayalarry；未知来源按行忽略，DIM 行不进入人工链。武器 ID 可在简表中留空，应用先按官方中文名称解析；名称无法唯一核对时才要求补充 ID。

禁止：

- `contains`、前后缀和“候选唯一”包含匹配。
- 简称、旧译、同义词和人工推断。
- 大师属性词干归类，例如“填装/装填”“操控/操控性”。
- 自动把“伤害”改成“冲击”。
- 无法证明时忽略错误并继续激活。

维护者生成器可以在写出 CSV 前依据明确的来源术语表完成一次性官方化，例如将来源中的“换弹”写成 Manifest 官方名称“填装速度”；导入器本身仍不接受简称或自动推断。所有严格栏位最终只允许写入已由当前 Manifest 精确确认的名称，已划除、已删除或无法确认的附加项只保留在来源证据中，不得从原始展示字段回填。

存在任一阻塞项时不得激活新人工来源数据。导入确认必须重新核对 CSV 指纹和 Manifest，并使用单事务整体替换。

### 3.4 DIM 原生规则

- 一条 DIM 规则保存一个完整 Hash 组合，组合内全部必需，多条组合任选其一。
- 不转成普通六栏计数，不跨组合累计 Perk。
- 同栏多个必需项、缺栏、特殊异域插槽和无法归栏 Hash 保留原始结构。
- 旧 Hash 只有在官方身份能够精确证明时才映射。
- 无法确认时显示“该 DIM 规则无法核对”，不能判定为未符合。
- 在线更新固定到准确 commit；网络失败继续使用上一次成功 revision。

### 3.5 旧 SQLite

新 schema 至少记录：

```text
semantic_validation_version
validated_manifest_version
人工来源 CSV 指纹
DIM revision 与原文件指纹
数据集激活状态
```

缺少当前语义标记的人工来源库固定为 `unverified`。旧文件可以保留供回退或人工查看，但不参与核心状态、排序、保护或留拆判断。新数据全量通过后才整体替换；不得自动修正旧库中的“伤害”等历史值。

### 3.6 核心 Roll

人工来源最多核对六项：

```text
Perk 1 / Perk 2
  > 第一列 / 第二列
  > 大师 / 起源特性
```

同一栏多个候选为“任选其一”，不同栏之间为“全部必须分别核对”。`x/y` 中的 `y` 是来源明确要求的栏位数，不是候选 Perk 数；`x/y` 只表示六项事实符合度，不是评分。

| 状态 | 含义 | 玩家文案 |
|---|---|---|
| `full` | 全部明确要求均符合 | 全部符合 |
| `core` | 至少要求一个核心 Perk，所有已要求的核心栏均符合，但其他栏位有缺失 | 核心符合 |
| `close` | 来源未要求核心 Perk，非核心要求部分符合 | 接近推荐 |
| `key_missing` | 来源要求的任一核心 Perk 栏不符合 | 关键缺失 |
| `not_matched` | 来源有明确要求，但当前实例一项也未符合 | 未符合 |
| `weapon_only` | 来源只推荐武器身份 | 仅推荐这把武器 |
| `uncheckable` | 实例或规则无法安全核对 | 无法判断 |

以上七种只用于单来源汇总和排序，不直接作为每个栏位的玩家文案。仓库卡片、同名 Roll 对比与详情逐栏统一使用以下 4 种事实：

| 逐栏状态 | 判定 | 玩家文案 |
|---|---|---|
| `match` | 本件拥有项按 Hash 或规范化官方名称命中任一来源候选 | 符合 |
| `different` | 目标栏数据完整但没有命中；或整件 Roll 完整但当前版本没有该栏位 | 不符 |
| `uncheckable` | 整件 Roll 未读取、目标栏确实不完整，或来源要求完全没有可比较名称与 Hash | 无法判断 |
| `source_not_specified` | 来源没有要求该栏位 | 来源未要求 |

来源名称没有解析出当前武器版本的 Hash，不能单独把完整本件数据覆盖为 `uncheckable`。只要来源仍有可比较的官方名称，且本件目标栏完整，就必须按名称继续判定为“符合”或“不符”。整件 Roll 完整但当前版本不存在目标栏时，结果为“不符”，详情补充“本版本无此栏位”。

单来源判定固定按以下优先级执行：

```text
存在无法确认的必需栏位 → uncheckable
没有任何栏位要求       → weapon_only
全部必需栏位符合       → full
任一已要求核心栏不符   → key_missing
核心栏全部符合         → core
无核心要求且部分符合   → close
其余                   → not_matched
```

只要求 Perk 1 或只要求 Perk 2 时，该单栏就是完整核心要求；不能因为没有“双核心”而降为 `close`。来源未要求 Perk 1/2 时，不得凭第一列、第二列、大师或起源特性伪造“核心符合”。

DIM 不使用六项权重。任一完整组合符合即为符合；没有组合符合时，优先显示可核对组合中的最接近结果；若仍存在可能符合但无法核对的组合，则显示无法核对，不能判为未符合。

推荐按武器身份共享，但每个 `instanceId` 必须使用自身实际拥有 Roll 独立计算。Manifest 可掉落池不得冒充实例 Roll。

多个来源始终独立保存结果，不跨来源累计 `x/y`。推荐列表只显示 5 类玩家结果：

- `符合推荐`：至少一个来源为 `full / core` 或 DIM 完整组合符合，且没有同用途的明确冲突。
- `部分符合`：存在正向符合与明确不符的来源冲突，或只有 `close / weapon_only` 等部分证据。
- `未符合`：有来源覆盖，所有可核对来源均未符合。
- `无法判断`：任一来源因本件 Roll 或规则本身缺少真实可比较数据而无法判断；安全原因优先显示。
- `无推荐`：没有任何启用来源覆盖。

`general` 与 PVE、PVP 都视为用途重叠；PVE 与 PVP 之间不直接构成来源冲突。首层存在多个来源时只显示结论和来源数量，不用固定来源顺序伪造权威高低；全部来源进入“查看依据”。

DIM 与四个人工来源使用同一用途冲突规则：DIM 完整组合符合与人工来源关键不符，或人工来源核心符合与 DIM 明确不符，只要用途重叠就在推荐列表显示“部分符合”。DIM 同一来源内部的多条组合仍是任选其一，不互相制造冲突。

强制保护包括：游戏内锁定、精确配装引用、玩家手动保留、独特 Roll、来源冲突、数据不完整、推荐库未覆盖或未验证。

### 3.7 来源管理与纠错

推荐数据必须允许玩家纠错，但不能直接破坏发布方原始数据。管理入口分为三个层级：

| 层级 | 玩家操作 | 生效范围 | 恢复方式 |
|---|---|---|---|
| 单条规则 | 移除某把武器下某来源的一条推荐 | 只停止该规则参与匹配、排序、推荐保护和批量整理 | 在“已移除规则”中恢复 |
| 整个来源 | 停用或移除 Aegis、LGpig、YXCRALLXY、Sayalarry 或 DIM | 该来源全部规则停止参与结论，其他来源继续工作 | 停用可直接启用；移除需重新导入或更新后显式恢复 |
| 当前数据集 | 删除当前人工推荐数据或移除当前 DIM Wishlist | 对应数据链进入“未配置”，不自动回退到旧库 | 重新导入、在线更新或显式选择可用历史版本 |

交互规则：

- 规则管理必须显示来源、武器、用途、完整 Perk 组合、当前数据 revision 和受影响的账号实例数，不能只显示难以辨认的内部 ID。
- 点击“移除规则”默认写入可恢复的本地排除记录。发布方原始规则保持只读，后续更新不会把玩家已经移除的同一规则静默恢复。
- 玩家自建的个人推荐仍使用现有独立管理能力，允许编辑、停用和永久删除，不与发布方来源混在同一列表。
- 来源状态固定为 `active / disabled / removed`：`disabled` 保留本地规则并排除匹配，可立即恢复；`removed` 删除该来源的本地规则并保留来源 tombstone，重新导入或更新后也不得静默启用，必须由玩家显式恢复。
- 停用或移除来源前显示规则数、覆盖武器数和当前账号受影响实例数；确认后只重算受影响来源覆盖的武器。
- 删除整份数据集属于破坏性操作，必须二次确认，并明确删除对象、当前 revision、恢复方式以及不会删除的账号标签、备注、锁定和配装。
- 删除当前激活数据后显示“未配置”，不得自动启用旧的 `unverified` 数据，也不得用残留匹配缓存继续给出结论。
- 导入新版数据时保留玩家的来源停用和规则排除设置。无法继续确认同一条规则身份时，将排除项标记为“需要复核”，不能静默套用或丢弃。
- 重新导入包含已移除来源的数据时，预览必须显示“该来源仍处于已移除状态”；只有玩家选择恢复后才重新参与匹配。
- 批量整理预览存在时禁止修改来源或规则；若推荐 revision 已变化，旧预览立即失效，玩家必须重新预览并确认。
- 批量标签使用一次本地批量提交；“待处理”提交前仍按结构化保护索引排除强保护实例，不逐件重复写入。

发布方数据和玩家纠错记录分层保存，避免更新、恢复和审计互相覆盖：

```text
recommendation_source_overrides
  source_id
  enabled
  updated_at

recommendation_rule_overrides
  source_id
  rule_stable_id
  enabled
  reason
  source_revision
  updated_at
```

`rule_stable_id` 必须来自来源、武器官方身份、用途和精确规则组合等稳定语义，不得依赖 SQLite 行号或界面顺序。原因可选，仅供玩家自己识别为何移除。

## 4. 缓存、刷新与性能

### 4.1 数据分层

| 数据层 | 内容 | 规则 |
|---|---|---|
| 稳定定义缓存 | Manifest、图标、装备定义、插槽定义、完整可掉落池 | 按 Manifest 版本持久缓存 |
| 推荐知识缓存 | 四人工来源、DIM Wishlist | 按数据 revision、commit、ETag 或指纹保存 |
| 派生计算缓存 | 实例推荐摘要、核心状态、六项证据 | 按 Roll 指纹和所有依赖版本保存 |
| 上次成功账号快照 | 仓库、角色背包、已装备、邮政官和实例 Roll | 只作启动占位、离线查看和失败回退 |
| 当前账号 Store | 本次运行最后一次 Bungie 确认状态 | 不使用 TTL，不允许静默后台替换 |
| Pending 操作层 | Bungie 写请求及确认进度 | 不冒充当前实体状态 |

上次账号快照无论多新，应用重启后都必须标记为“上次同步数据”。仓库不建立独立缓存，它是当前账号 Store 的派生视图。

`dim-api` 只作为数据边界参考，不引入依赖、不复制代码，也不调用 DIM Sync。它证明 DIM 自己也只持久化标签、备注、配装和设置等应用数据，不保存 Bungie 实时库存。组件增量和离线更新队列只用于应用自有数据，不能套到 Bungie Profile。

匹配缓存键至少包含：

```text
accountKey + instanceId + itemHash + rollFingerprint
+ manifestVersion + knowledgeRevision + dimRevision
+ recommendationOverrideRevision + matchingAlgorithmVersion
```

位置、光等、锁定、装备状态和玩家标签不进入 Roll 指纹。

### 4.2 统一账号同步

账号、仓库和设置页的同步入口调用同一个权威动作：

```text
Bungie Profile
  → 紧凑账号快照
  → 实例差异
  → profile_minted_at 水位线检查
  → 原子提交当前账号 Store
```

实例差异只区分新增、删除、位置、锁定、装备和 Roll 变化。仓库同步关键路径不得包含标签读取、CSV 校验、推荐库重建、全账号推荐重算、完整可掉落池或同名实例详情。

刷新所有权固定为：

- 主进程启动只恢复资料库运行时、上次账号快照和稳定本地资源，不远程刷新账号。
- 全局账号控制器每次运行只执行一次可见初始同步。
- 页面挂载、切换菜单和打开详情不触发账号同步。
- 推荐核对只在账号快照已经提交后作为非阻塞派生任务启动；菜单挂载不拥有推荐刷新动作，位置等非 Roll 变化通过匹配缓存直接复用。
- 攻略匹配、助手匹配等只读消费者只读取当前全局账号快照；配装执行前后的复核必须调用全局账号控制器，不得在功能内部保留直接强刷 Profile 的 fallback。
- 手动同步穿透账号缓存；普通请求不能阻挡或替代权威请求。
- 同步失败保留当前 Store；本次运行尚未成功同步时继续显示明确标记的历史快照。
- 首页情报、账号战绩、商人和资料库分别维护自己的刷新范围与时间。

禁止账号固定轮询、TTL、stale-while-revalidate，以及只更新 Session、Repository 或磁盘但不提交 Renderer Store 的后台刷新。

账号写后一致性继续由 [Bug #22](Bug-22-account-refresh-write-consistency.md) 跟踪。

### 4.3 写操作确认

转移、锁定、装备、邮政官取回和配装统一使用：

```text
提交中 → 请求已受理 → 正在确认 → 已确认并提交 Store
```

- Bungie 明确返回成功后立即把成功项投影到共享账号 Store，并登记 Pending；界面显示预计目标和“正在确认”，最后确认快照仍单独保留服务器事实。
- Profile 确认后才更新账号 Store 并显示成功。
- 后台确认由写操作事件触发，按账号和 Profile 组件合并有限次数读取；不得启动永久轮询线程。
- 超时、网络不可用或有限确认后 Profile 尚未前进时显示“等待游戏状态”并保留预计位置；只有更新 Profile 明确冲突时才清除 Pending。
- 玩家手动同步优先于后台确认，并以服务器结果重新判定 Pending。
- 多个写操作按账号和 Profile 组件合并确认，不为每件装备重复刷新完整 Profile。
- 标签、备注和玩家整理状态属于本地写入，持久化成功后可直接更新本地 Store，不进入 Bungie Pending。

### 4.4 推荐增量更新

| 账号变化 | 页面处理 | 推荐处理 |
|---|---|---|
| 位置、锁定、装备变化 | 更新实例事实 | 复用匹配结果 |
| 新增实例 | 添加卡片 | 只计算新实例 |
| 删除实例 | 删除卡片 | 删除对应摘要 |
| Roll 指纹变化 | 更新实例 Roll | 只重算该实例 |
| Manifest 或推荐 revision 变化 | 保留账号事实 | 按依赖版本失效 |
| 来源停用或规则移除 | 保留账号事实 | 只重算该来源覆盖的受影响武器 |

运行时只读取已经激活的推荐 SQLite。CSV 预览、语义校验和知识库重建只在导入或更新阶段执行。账号同步后不得无条件重新扫描全部武器。

### 4.5 详情渐进加载

详情首屏由四类本地数据组合，不等待一个“完整详情对象”：

```text
当前账号 Store：位置、锁定、光等、当前实例 Roll
Manifest 缓存：名称、图标、框架、属性和说明
推荐缓存：核心结论与来源摘要
本地数据：标签、备注和配装保护
```

- 点击后立即显示首屏，不出现详情全局 Loading。
- 完整可掉落池默认折叠，玩家展开后才按 `itemHash + manifestVersion` 从本地 Manifest 读取并持久复用。
- 实例完整 Roll 默认折叠，玩家展开后才按 `instanceId + rollFingerprint` 读取；相同实例未发生 Roll 变化时跨详情和同名整理复用。
- 打开详情、进入同名组或切换同名实例不得自动读取实例完整 Roll。玩家在同名组选择“完整 Roll”后，才使用有并发上限的队列逐件补齐，并允许单件重试。
- 当前启用 Perk 来自账号紧凑快照，应立即显示，不得等待实例完整 Roll。
- 实例插槽配置只在摘要不足、玩家主动展开、主动重新读取或写后确认需要复核时访问 Bungie。
- 打开详情不得触发全账号刷新。
- 同名整理直接使用紧凑 `weapon_roll`，切换同名组不得并发读取组内所有实例详情。
- 相同 Roll、Manifest 和推荐 revision 下，重复打开同一武器不重新读取或计算。
- 延迟数据只更新自己的固定区域，不能让弹窗主体结构在数秒后跳变。

### 4.6 显式工作流与渐进披露

仓库使用三个始终可见、可直接跳转的任务入口：`1 浏览装备`、`2 看推荐`、`3 整理同名`。它们是玩家路径，不是必须依次完成的向导。

“看推荐”首屏只保留：

- 一个当前任务说明，例如“先看符合推荐，再处理部分符合与无法判断”。
- 先选择 Aegis、LGpig、YXCRALLXY、Sayalarry 或 DIM，再按该来源的 `符合推荐 / 部分符合 / 未符合 / 无法判断 / 未收录 / 全部` 筛选；用途、位置和玩家标记等收入“更多筛选”。
- 武器身份、真实位置、核心状态、最多一条主要来源摘要和“查看依据 / 整理同名”操作。
- 一个“推荐来源”入口，负责数据更新、来源停用、按来源删除和单条规则移除。

以下内容不得常驻推荐结果首屏：

- 四格核对统计、来源状态长列表和重复的结果解释条。
- DIM 规则总数、短 commit、CSV 来源记录数和逐阶段扫描文案。
- “复制验收报告”等维护者操作。
- 本地文件、粘贴文本、标准模板等低频导入方式。

正常状态应保持安静：账号同步与推荐核对完成后只保留短状态和时间。异常、部分可用或数据未配置时，在固定状态区显示原因和唯一主操作，不让异步完成造成页面整体跳动。

详细信息按层级进入：

| 层级 | 内容 |
|---|---|
| 结果行 | 玩家此刻需要做的判断和下一步操作 |
| “查看依据”详情 | 六项证据、全部来源、用途、规则说明和保护原因 |
| “推荐来源”覆盖层 | 来源启停、按来源删除、单条规则移除、更新与恢复 |
| “其他导入方式” | 本地文件、粘贴文本、模板导出和高级维护 |
| 设置诊断 | 核对数量、规则总数、revision、commit 和验收报告 |

覆盖层打开后限制焦点，关闭后返回触发按钮；三个任务入口和结果列表使用 roving focus。窄屏保持同一信息顺序，结果行改为纵向布局，来源管理使用全高覆盖层，不维护另一套页面。

### 4.7 浏览装备的推荐筛选与单件快捷操作

武器浏览模式在顶部工作流栏按“先来源、后结果”筛选。来源只列当前已配置且启用的 Aegis、LGpig、YXCRALLXY、Sayalarry 和 DIM；即使某个来源在当前账号或当前筛选范围内覆盖为 0，也必须保留在来源选择中，不能因没有命中实例而消失。未选择来源时显示全部当前范围装备，不提供容易混淆的多来源综合结果筛选。选择来源后显示 `全部 / 符合推荐 / 部分符合 / 未符合 / 无法判断 / 未收录`，并与“看推荐”消费同一个单来源实例分类函数；`未收录`只表示所选来源没有该武器规则。数量随搜索、位置、槽位、类型、稀有度、锁定、整理状态和保护信号等其他条件变化，但计算各分类数量时忽略当前推荐结果筛选。推荐核对未完成时，没有现成实例结果的武器不得计入“未收录”。所选来源在卡片和结果行中固定优先展示，切换到护甲或装备时重置来源与结果筛选。

左侧带数量的筛选项采用分面口径：每个选项应用除自身维度外的其他已生效条件，选中项数量应与切换该维度后可得到的结果一致。物品范围明确显示账号总数；武器槽位、查看范围、武器类型和框架显示当前其他条件下的可用数量，不能一部分使用全账号固定总数、另一部分使用当前结果数。

单来源分类必须先为账号武器建立一次实例结果索引，结果按钮、装备列表和各分面数量复用该索引，不得在每个分面内重新遍历来源摘要。只切换来源且结果仍为“全部”时，槽位、位置、武器类型和框架的候选范围没有变化，不应重新扫描这些分面。

浏览装备卡片在非整理模式提供两个单件快捷操作：

- `加锁`：仅对有实例 ID 且当前未锁定的装备可执行；已锁定时显示稳定状态，不重复提交。
- `取出`：仅对仓库中的实例显示，目标固定为当前角色；角色背包、已装备、邮政官和其他角色装备不伪装成可直接取出。

两个操作都不弹二次确认，因为它们是可逆的显式单件动作。一次只允许执行一个快捷写操作；当前按钮显示进行中，其他快捷按钮暂时禁用。失败后保留卡片并显示 Bungie 返回的真实原因；加锁成功后焦点回到同一卡片主入口，取出成功且卡片离开当前仓库结果时，焦点移动到下一件，末项则回到上一件。快捷按钮必须作为卡片主按钮的兄弟节点，保持 Tab 可达，不能形成嵌套按钮；武器虚拟网格的固定高度、测量步长和焦点恢复必须同步更新。

## 6. 验收条件

### 数据与匹配

- 四人工来源与 DIM 原生 Wishlist 完全拆分。
- 四人工来源在当前 Manifest 下严格校验为 0 阻塞。
- “操控 → 操控性”“伤害 → 冲击”等宽松关系被阻止。
- 旧人工来源 SQLite 未验证时不参与任何结论。
- DIM 原始组合、说明、标签和不可确认 Hash 不丢失。
- 每个实例使用自身 Roll，核心状态只看来源要求的 Perk 1/2。
- 同为 `5/6` 时，缺低优先级项与缺核心 Perk 显示不同结论。
- 暗夜魅影光等 413 的 Aegis 结果应为 `Perk 0/2 · 完整 2/6`；大师“填装速度”与本件“大师杰作：稳定性”明确显示“不符”，不能出现“数据未读取”或“待核对”。
- 暗夜魅影光等 324 的大师与起源特性均应显示“不符”，不能因为推荐 Hash 未解析而进入未知状态。
- 老版本武器完整 Roll 没有起源栏时显示“不符”，详情中的本件值显示“本版本无此栏位”。
- 单条规则移除后只影响对应来源与武器，且可以恢复。
- 整个来源停用后不参与匹配、排序、推荐保护或批量整理，其他来源不受影响。
- 删除当前人工推荐数据或 DIM Wishlist 后进入“未配置”，不会回退到旧的未验证数据。
- 导入新 revision 不会静默丢失或错误套用玩家的来源停用与规则排除设置。

### 缓存、刷新与性能

- 本次运行只有一次可见初始账号同步，没有主进程与 Renderer 双刷新。
- 账号、仓库和设置页共用唯一权威同步，仓库不存在独立远程缓存。
- 游戏内移动装备后，同步一次即可同时更新账号、仓库和配装。
- 权威结果不会叠加未确认 patch，晚到旧 Profile 不会恢复旧位置。
- 写接口成功后立即更新共享页面投影并显示 Pending；确认快照与预计状态保持分层。
- 仓库同步不等待推荐重算、CSV 校验、完整池或同名实例详情。
- 位置、锁定、装备和标签变化不重新计算相同 Roll。
- 同一武器重复打开不重新读取已有定义、当前 Roll、推荐摘要或完整池。
- 完整池只在玩家展开后加载；同名组不自动读取全部实例详情。
- 人工推荐 CSV 自动校验按文件状态与 Manifest 版本记忆结果；同一份阻塞数据不会在每次打开详情或重新核对仓库时重复执行完整校验。
- 详情推荐摘要按账号/Manifest 作用域、推荐 revision 与武器身份复用，并对并发请求去重；来源或规则变化后使用新 revision 自动失效。
- 同名整理的完整 Roll 结果、读取状态和并发请求统一按实例当前 Roll 指纹保存；账号同步导致 Roll 改变后不会继续复用旧对比数据。
- 详情缓存作用域只使用账号身份、Manifest 版本和语言；同版本资料库仅更新时间变化不会清空定义、Roll 或推荐摘要缓存。
- 持久化实例详情 SQLite 按账号、Manifest 版本和实例 ID 隔离；资料库升级后账号 Session 与完整 Roll 缓存同时切换版本，不会复用旧定义构建的详情。
- 页面不存在账号固定轮询、切页刷新或静默替换列表。
- 推荐删除只触发对应推荐 revision 的事件更新，不触发 Bungie Profile 或全账号同步。

### 安全与 UI

- 卡片、推荐结果、同名整理和详情使用相同核心状态。
- 详情中的人工来源以“图标 + 名称 + 短状态”表达同栏候选“任选其一”；名称必须常驻可读，同名多 Hash 合并成一个玩家候选。只有本件实际命中的候选使用绿色边条和勾，当前启用同时使用独立蓝点与“当前”文字，未命中的合法备选不显示红叉或整体灰隐。
- 推荐 Perk 图标可通过鼠标悬浮、键盘聚焦和触屏点击查看官方名称、说明、来源身份与本件状态；关闭支持 `Escape` 和点击外部，缺少图标时保留可读文字回退。
- DIM 继续按独立完整组合显示，组合内逐项使用相同的图标、常驻名称与命中状态，不把多套组合合并成候选池，也不使用与命中语义重复的拇指标记。
- 首层直接显示“浏览装备 → 看推荐 → 整理同名”，无需理解数据源或核对流程才能开始使用。
- 推荐结果首屏不常驻核对矩阵、来源长列表、规则总数、revision 或验收报告。
- 选择具体来源后，`符合推荐 / 部分符合 / 未符合 / 无法判断 / 未收录` 能直接到达该来源对应实例，详细来源和六项证据按需展开。
- 浏览装备顶部与推荐结果列表使用相同的“来源 → 该来源结果”分类；数量跟随其他条件变化，核对未完成的未知实例不进入“未收录”。
- 正常状态只显示短状态和时间；异常状态提供原因与唯一主操作，异步更新不改变主体布局。
- 单件和批量锁定显示保护项、成功项与失败项。
- 非整理模式的实例卡可一键加锁；只有仓库实例可一键取出到当前角色，失败时保留卡片并显示真实原因。
- 单件加锁后焦点回到原卡片；取出导致卡片离开结果时焦点进入相邻卡片，快捷按钮可通过 Tab 到达且不与卡片主按钮嵌套。
- 推荐结论不自动修改玩家标签或游戏锁定状态。
- 强制保护项不会进入自动操作。
- 移除规则、停用来源和删除数据集前显示具体影响范围；删除数据集必须二次确认。
- 推荐数据操作不清除玩家标签、备注、游戏锁定或配装引用。
- 批量整理预览期间不能修改推荐规则；revision 变化后旧预览不得继续执行。
- 最终分解只能由玩家在游戏内完成。
- 护甲页面、护甲筛选和 Armor Planner 不受影响。

## 7. 不在范围

- 自动或远程分解 Destiny 2 装备。
- 自动创建配装或覆盖玩家标签。
- 接入或调用 DIM Sync API。
- 把未获授权的第三方资料打包进公开安装包。
- 批量抓取或镜像 light.gg。
- 使用 AI 猜测武器、Perk、版本或作者未表达的组合。
- 护甲清理和 Armor Planner 规则改造。

## 8. 完成条件

代码开发状态与数据内容状态分开：S0–S11 代码已经完成开发；真实账号与实窗验收通过，并且四人工来源外部数据严格校验达到 0 阻塞后，T20 才能标记为全部完成。

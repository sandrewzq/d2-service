# T41：邮政官安全处理

> 状态：📝 候选方案，待排期
> 优先级：P0
> 类型：高风险 Bungie 写操作
> 前置条件：✅ [T40 账号容量与风险摘要](T40-account-capacity-risk.md) 已满足
> 账号菜单合同：[应用工作区账号章节](../references/ui-specs/application-workspaces.md#账号)

## 1. 目标

在现有单件邮政官取回能力上增加可解释、可确认、可部分成功的安全批量处理流程，避免玩家点击后才发现背包已满或应用状态与游戏状态不一致。

参考 DIM 的邮政官取回和腾空间能力，但本项目必须先展示计划、保护对象和逐项结果，不采用隐式自动搬运。

## 2. 范围

- 计算当前可直接取回、因目标槽位已满而无法取回和预计剩余数量。
- 执行前列出每件物品、目标槽位、预计动作和阻断原因。
- 允许玩家取消计划或只执行当前可安全完成的项目。
- 批量结果逐项展示成功、失败和等待游戏状态确认。
- 写操作成功项立即投影到中央账号 Store，后续由更新的 Profile 确认。

后续如增加“为邮政官腾出 N 格”，必须明确展示将移动的具体装备，并保护：

- 当前已装备物品。
- 已锁定物品。
- 应用配装与游戏内配装引用物品。
- 高光等保留物品。
- 玩家明确标记为保留或待定的物品。

## 3. 写操作与同步约束

- Bungie 返回单项成功不等于整个批次成功，禁止使用统一成功提示覆盖失败项。
- 接口成功但 Profile 尚未反映时显示“等待游戏状态”，不能立即回滚预计位置。
- 只有更新的服务器版本明确冲突时，才能撤销本地预计状态。
- 批量操作必须复用账号写结果和 Pending 确认语义，不建立邮政官私有刷新链。
- 计划生成后如果账号 Profile 已前进，执行前必须重新校验容量和物品位置。

## 4. 非目标

- 不实现后台持续自动搬运。
- 不实现无确认的 Farming Mode。
- 不自动拆解物品。
- 不为了腾空间移动受保护装备。
- 不把部分成功显示为全部成功。

## 5. 验收标准

- 玩家执行前能准确知道哪些物品会被取回、哪些不会以及原因。
- 角色背包已满时不会发送已知必然失败的取回请求。
- 批量中单项失败不影响其他已成功项目的正确状态。
- 游戏已完成转移但 Profile 延迟时，应用不会短暂显示成功后又恢复旧位置。
- 跨设备或游戏内同时操作造成冲突时，页面能够区分等待确认和明确冲突。
